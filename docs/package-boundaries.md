# Package Boundaries

## Repository layout

```text
eval-platform/
├── packages/
│   ├── eval-contracts/
│   ├── eval-dataset/
│   ├── eval-runtime/
│   └── eval-metrics/
└── apps/
    ├── eval-api/
    ├── eval-web/
    └── eval-cli/
```

The four package workspaces keep the package boundary stable. `eval-runtime` contains runtime orchestration; `eval-dataset` contains Dataset/Data management, validation and serialization. Persistence implementations and application integration remain outside these package cores. Applications additionally contain `CONTEXT.md`.

The deployment source for the SP Harness is a fixed SP Git branch resolved to a commit during one Eval release workflow. That workflow deploys an independent Eval SP API/database, Agent Worker, Space Worker, DO namespaces and R2; all Eval SP calls, including login and Agent Config, target this deployment. Deployment orchestration is repository-level work, not another workspace package. See [Eval SP deployment](eval-sp-deployment.md). The source branch belongs to Project, while each Run records the actual source commit; Sampling does not own a branch.

Package-internal submodules:

```text
eval-dataset/
└── dataset/

eval-runtime/
├── plan/
├── harness/
└── runtime/

eval-metrics/
├── evaluators/
├── aggregation/
└── reporting/
```

## Dependency direction

```text
eval-contracts → eval-dataset → eval-runtime → eval-metrics
                        ↓             ↓             ↓
                       eval-api / eval-web / eval-cli
```

The arrows describe allowed consumption direction. The contract package must not depend on runtime, storage, API, Web, CLI or Cloudflare bindings; only its `./http-errors` and `./http` subpaths depend on `@springbrand/http` and `hono`.

## Package responsibilities

### Evidence export and import

The existing Harness/EvidenceStore seam owns one immutable evidence bundle per successful Subject execution. The Harness exports produced artifacts, original Subject Material files resolved from the Project's fixed references, and the complete raw source trajectory in order. EvidenceStore stores both file groups by content hash and splits trajectory JSONL at event boundaries within the file byte limit; it never normalizes or discards source event fields. The manifest records Subject input identities, artifacts, ordered trajectory parts with sizes/hashes/event counts, completeness and explicit artifact omissions. Runtime passes only the frozen Subject Material references to export, never live Dataset contents. An Evaluator receives its own initialization first, then all evidence files, and the manifest last; the SP adapter uses the public package's evidence path helpers and checks path, size and hash receipts. An event larger than the file limit is never dropped or truncated: the export fails with an explicit non-retryable error before any part is stored, and the SP import likewise refuses a bundle with a file above SP's per-file limit before writing anything.

Export is resumable without a second job store. `EvidenceStore.resume()` freezes the listing and `exportedAt` on the first pass, stores each missing artifact/Subject input by content hash and continues trajectory parts from a persisted source cursor (`ExportedEvidence.readTrajectory(afterSeq)`), then writes the deterministic manifest once; without saved progress it starts a new export. Runtime persists that progress after every stored file or part as `Sampling.evidenceExport` through the conditional Sampling update, bound to the Subject Submission ID that `Harness.exportEvidence` also receives; progress of another Submission is never reused. A later pass reads only what is missing, so the same evidence ID results. After `EVIDENCE_EXPORT_MAX_PASSES` failed passes, or a non-retryable failure, the execution fails with `evidence export failed…`, keeping its output and progress; a manual recollection resumes that progress with a fresh pass budget. Export failures never resubmit or restart the Subject Agent, and Evaluations stay queued until the bundle is stored. No legacy single-file trajectory or alternate Workspace initialization branch is retained.

### `eval-contracts`

Owns stable runtime/evaluation types shared across packages: Project and its fixed plan (`ProjectPlan`, `ExecutionPlan`, `EvaluationPlan`, `ProjectDatasetSnapshot`, `AgentConfigSnapshot`, `EvaluationOutputSchemaRef`), Sampling, EvaluationRecord, `RunOperation`, `RunTargetSelector`, `RunTargets`, `RunRequest`, HarnessConfig, ExecutionOutput, EvaluationAgentOutput with its raw `structuredOutput`, `AgentObservationRef`, ArtifactRef, TrajectoryRef and EvidenceRef. Project carries metadata and the selected deployment's SP source branch; its execution plan is fixed at creation, and its optional evaluation plan is replaceable until the first pipeline/evaluation Run locks it. The Run operation is chosen per Run and never stored on Project. Run records the deployed source commit at admission as provenance, without adding a branch to Sampling. Dataset/Data belong to `eval-dataset`; ProjectSample, the Project's full copy of one Data, belongs to `eval-runtime`. Evidence and explanations remain Evaluation Agent outputs, not an independent attribution contract. The status vocabularies (`SAMPLING_STATUSES`, `PENDING_SAMPLING_STATUSES`, `AGENT_STATUSES`, `TERMINAL_AGENT_STATUSES` and their predicates) are defined only here; SQL uses the same constants. `AgentSubmission.status` is SP's normalized status; SP's raw status is mapped once in the Harness adapter. The Eval API error-code catalog (`./http-errors`, built with `defineErrorCatalog`) and its Hono responders (`./http`) also live here; the HTTP contract is in [Eval HTTP control plane](eval-http-api.md).

An owner-scoped output-format catalog holds standalone named draft 2020-12 JSON Schema files with immutable bodies; the evaluation plan stores the selected ID and its content digest. Every pipeline/evaluation Run requires an evaluation plan. Runtime resolves the Schema by ID, even after its catalog entry is soft-deleted, and every Evaluation Agent receives it at the fixed path `/evaluation-output.schema.json` in its confined Workspace before submission (see [Eval SP Harness](eval-sp-harness-protocol.md)).

It is the only place for cross-package evaluation contracts. `InitialResourceFile` describes an initial resource's read-only file inventory (`path`, `mediaType`, `byteSize`) shared by API and Web; bytes remain in the API's existing Bundle directory. `AgentResourceSnapshot` carries unchanged SP usage events, telemetry events and billing settlements with collection scope and source-completeness metadata. Stage records carry only `AgentResourceState` (status with scope or a `summarizeResourceSnapshot` summary, download count, `exhausted`); `AgentResourceCollection` is that state with its stored snapshot loaded. `jsonObjectInPlaceSchema` and `jsonObjectArrayInPlaceSchema` validate large raw records (one object, or an array such as a snapshot's events) by the same JSON rules without copying them or their array; the Eval API wire parser and Runtime both use them. It does not implement orchestration, persistence, normalization, aggregation or pricing.

### `eval-dataset`

Owns Dataset/Data schemas, required current `userPrompt`, optional per-Data `evalPrompt`, arbitrary additional JSON business fields, initial-session references, separate Subject `initialMaterials` and Evaluator `evalInitialMaterials` reference lists, JSON/YAML serialization, strict prompt JSON/JSONL upload parsing and `createDatasetService(store)`. Dataset and Data are scoped to one Eval SP user by the application Store; Data is reusable across that user's datasets through explicit associations, not per-dataset copies. Dataset/Data are the editable source catalog: Project creation copies the selected Dataset metadata, member order and full Data into the Project snapshot, so later edits, detachment or soft deletion never change an existing Project. The pure Dataset package does not authenticate users or store SP accounts. Dataset and reference objects are strict; Data preserves arbitrary extra JSON business fields while validating known fields. Both prompts preserve their original text and reject blank values when supplied. `userPrompt` is required for Subject execution; `evalPrompt` is required when an Evaluation or Pipeline Run is admitted, while execution-only Data need not provide it. Prompt import also requires `evalPrompt`, `name` and `description` on every row and Dataset `description` alongside the file; the application Store persists an internal Prompt Dataset kind and preserves those requirements on later updates and membership changes. Extension fields cannot override the generated `dataId` on creation.

JSON numbers must be finite, and integers must stay within JavaScript's safe-integer range at every input, persistence validation and serialization boundary. Larger integer identities must be supplied as strings; the package rejects them rather than coercing or rounding them. YAML integers are parsed as BigInt and range-checked before conversion. JSON and YAML reject duplicate property names within each object; JSON checks decoded property names before native parsing can discard earlier values and does not accept JSONC extensions.

`InitialSessionRef` contains required `bundleId` and `sessionId`; `InitialMaterialsRef` contains required `bundleId` and `materialId`. `initialSession` is one optional `InitialSessionRef`. Subject `initialMaterials` and Evaluator `evalInitialMaterials` are each an optional, non-empty, ordered array of `InitialMaterialsRef`: absent means no materials, `[]` is rejected, and the same `(bundleId, materialId)` may not appear twice in one field. References in one field may name Materials of different Material Bundles. Array order is preserved and is part of the Data content, so it affects the Project execution plan digest and Dataset import identity comparison. Every reference identifies a resource within a Bundle rather than the Bundle alone: a material reference names a Material Bundle and a session reference a Session Bundle, two independent catalog resource types defined in [Dataset upload](eval-dataset-upload.md). Every material reference must resolve to uploaded files before initialization. Reference IDs are platform UUIDs validated by `platformIdSchema` and canonicalized to lowercase; the Dataset package does not generate or infer references. The Eval API's owner-scoped resource catalog generates Material Bundle, Session Bundle, Material and Session UUIDs when users upload resources. Generator specs and inline resource bodies are not accepted as references. The initialization Session identity is not the active Chat/Submission identity. Eval's owner-scoped Bundle directory holds canonical Session JSON/JSONL; SP owns importing supplied context into the Chat Session, framework-native formats, tool-call schemas and Context reconstruction. The current task is the required `userPrompt`, not a field inferred from generic data or Session history. Dataset does not own a second Session store.

The internal files are `dataset/model.ts`, `dataset/input.ts`, `dataset/serialization.ts`, `dataset/store.ts` and `dataset/index.ts`; the package exposes only its root entry. Every user-input failure becomes `DatasetInputError`, and `parseStrictJson` is the single duplicate-key-rejecting JSON parser shared with the Eval API. Creation uses native UUIDs; editable-field updates are full replacements. Every platform UUID (Dataset, Data, Material Bundle, Session Bundle, Material, Session, output format) is validated by the one exported `platformIdSchema` and canonicalized to lowercase, following SP's Zod UUID normalization pattern. Import, duplicate detection, service queries, Store comparisons and returned snapshots use that canonical identity. Resource reference IDs use the same canonical form so catalog lookup, Bundle file resolution and deletion checks agree; Data business fields remain unchanged. Serialization has no persistence side effects. Import assigns missing IDs and submits a complete `DatasetSnapshot` through one atomic Store command. Existing IDs may be reused only for identical content; conflicting imports never overwrite or partially commit. Deleting a Dataset preserves shared Data; deleting referenced Data is rejected atomically. Export reads one consistent Store snapshot.

`DatasetStore` is the application-injected PostgreSQL persistence port. Its implementation must follow SP's transaction, uniqueness and foreign-key constraint pattern, not instantiate a database client inside the Dataset package or rely on service-side prechecks. It validates owner-scoped active Material references in a Material Bundle and Session references in a Session Bundle in every Data write path, including general create, update and import; a soft-deleted resource cannot be newly referenced. Catalog deletion is blocked while active Data binds the resource and otherwise uses a `deleted_at` marker, consistent with SP's soft-delete pattern; resource files are never physically deleted, so Projects keep reading their references by ID. File bundles remain references to existing material capabilities; the package does not generate manifests/hashes, upload/download files, own an R2 binding or operate DO storage. Runtime/Harness owns materialization through public Workspace boundaries. SP's private workspace helpers are not copied or imported across repository source paths.

### `eval-runtime`

`ProjectView` owns the shared Project read projection (plan, ProjectSamples and ProjectRunState); API persistence and Web consume it from this package. `ProjectRunState` carries the existing Run sequence and a `CurrentRun` derived from `RunSnapshot`, without another persisted lifecycle state.

The API process constructs the admission interface (`createEvalRunAdmission`) without a Harness credential; only the Worker constructs the resume interface (`createEvalRunResumer`) with a real Harness. Both read the same `ProjectPlanReader` and `RuntimeStore` ports.

Owns the `plan` submodule (`normalizeExecutionPlan`/`normalizeEvaluationPlan` as the single plan validation and normalization boundary with explicit retry defaults, `digestExecutionPlan` and `digestJson` for evaluation plans, Schemas and fingerprints, `phasesOf(operation)`), `EvalRunAdmission.preview`/`submit`, `resume`/`interrupt`/`stop`, the `EvalRunQueries` read contract, Sampling lifecycle, separate execution/evaluation concurrency limits, retry, evaluation-input materialization and the `RuntimeStore` persistence port. Runtime inputs come only from the read-only `ProjectPlanReader` (`getProjectPlan`, `getProjectSamples`, `getEvaluationOutputSchema`) and `RuntimeStore`; Runtime never reads live Dataset/Data, editable Agent Configs or any configuration table. Admission (`preview` and `submit`, one `RuntimeStore.admitRun()` transaction) is described once in [Run admission](architecture.md#run-准入与独立评估); the Store port contract is the `admitRun` comment in `packages/eval-runtime/src/runtime/store.ts`. Resume rejects a Run whose `planDigests` no longer match the Project plan. Run status is a derived query projection from Sampling and EvaluationRecord state, not a separately persisted RuntimeStore field. SP is the first-party Harness contract inside this boundary; `apps/eval-api` composes its concrete public HTTP/WebSocket client, and a separate `eval-sp-adapter` package is intentionally not created.

Run binds the Samplings and EvaluationRecords it actually processes to an immutable scope of actual phases derived from its operation: execution, evaluation, or execution followed by evaluation (pipeline). `RunPhase` contains only `execution | evaluation`; `RunPhases` allows only those three valid scopes. A Run is the same generic query handle for each operation, not a separate Pipeline entity. `getRun()` derives both the current phase and status from the scoped child states. A pipeline Run coordinates the two real phases through independent per-Sampling execution and evaluation queues, and failure handling follows the next unfinished phase without adding a Pipeline-specific persisted state branch.

Harness exposes `ensureAgent`, not an unconditional creation operation. SP Chat is the persistent Session; each prompt submission within that Chat has its own SP Submission ID. Runtime assigns and persists the Subject `subjectChatId` or Evaluator `chatId` before calling SP, then passes it through the ordinary Inbox/Chat creation seam of the independent Eval SP deployment. Repeated or concurrent ensures for the same Chat identity must return the original Agent handle. An identity already bound to a different owner, Project, Sampling, role, framework, Agent Config or `evaluationId` must fail without rebinding or creating another Agent. SP owns authoritative deduplication and provisioning; Runtime owns identity persistence and operation-specific retry decisions, not a second local creation registry.

The execution, pipeline and evaluation operations share one Run-admission rule: a Project-scoped `idempotencyKey`, at most one unfinished Run per Project, a required evaluation plan for pipeline/evaluation (locked by the first such Run), and atomic replacement of only the selected records; the Store, not Runtime memory, is the source of truth. The complete rule is described once in [Run admission](architecture.md#run-准入与独立评估).

Project stop is owned by `eval-runtime` through the `withRunDispatchGate()` Store port and `stop()`; its lifecycle is described once in [Run scheduling and stop](architecture.md#run-调度与停止).

Fixed ProjectSample input belongs to the Project plan, not to each Sampling record. `SamplingState` contains only run-specific Sampling state and its `projectSampleId`; `EvaluationRecord` independently owns evaluator, submission, attempts, status and output, linked by `samplingId`. Execution consumes a temporary `RuntimeSamplingContext`; evaluation consumes a temporary `RuntimeEvaluationContext` that joins Sampling, EvaluationRecord and ProjectSample. Store commands never include those temporary contexts, and `getSampling()` returns a separate flat `SamplingSnapshot`. Admission and recovery read Sampling states through `RuntimeStore.getSamplings()`/`listProjectSamplings()` and distinct ProjectSamples through `ProjectPlanReader.getProjectSamples()` in bounded batches; recovery likewise reads EvaluationRecords through `RuntimeStore.getEvaluations()`. Batch ports preserve caller order and report missing items as null; a missing or mismatched input never clears results or starts an Agent.

`ProjectSample` is `{ projectSampleId, projectId, dataId, datasetIds, samplingCount, data: Data }`: the platform identity, the source Data ID, every bound Dataset in binding order, the fixed Sampling count and a full copy of the Data taken at Project creation. Shared Data bound by several selected Datasets is one ProjectSample. Runtime input preparation consumes this single shape. A business `sampleId` inside Data remains arbitrary JSON and is preserved for both Subject and Evaluation Agent initialization. Only Data's platform `dataId` is stripped from the Agent input. Sampling does not copy Data again.

`HarnessConfig.kind` selects the SP hosting boundary, while its required `framework` selects the Subject engine: `sp`, `codex`, or `cc` (Claude Code). All three use the same public Chat/Submission/Workspace lifecycle, not an eval-owned CLI or process launcher. The evaluation plan requires the SP framework and a frozen Evaluator Agent Config copy. The Subject framework is part of the execution plan digest, the request fingerprint and immutable Agent creation facts. `ensureAgent` receives it and returns a handle bound to that framework; subsequent operations use that handle, and retries cannot silently switch engines. Missing or unsupported frameworks fail configuration validation without falling back to SP. The eval-side boundary assumes SP provisions the selected engine; this change does not implement cloud provisioning in SP.

Before a Subject's first submission, `materializeInitialData()` receives Data's business fields except `evalPrompt`, `evalInitialMaterials` and platform ProjectSample/Data identities. Eval resolves the Subject's ordered `initialMaterials` references to file bytes and sends them through the SP initialization route; SP writes them to the target Chat Workspace. Every referenced Context must resolve to its immutable uploaded content, which SP imports before the first Submission; missing content fails initialization. The current `userPrompt` is then submitted unchanged, not wrapped with business data or Session history. Its stable initialization idempotency key is scoped to the target Chat/Session identity; repeated calls return the original preparation result without restoring over an advanced Session, and conflicting initialization facts are rejected. Runtime stores no second preparation registry. A restart continues the existing Agent Session and does not reapply the seed. Session references and bodies are not included in the execution prompt or Sampling persistence. An Evaluation Agent is an ordinary Agent with its own Chat, Session and Space; it is not bound to the Subject. It reads the Subject only through the imported evidence bundle under `/evidence/`: artifacts as primary evidence, the `sp-trajectory/v1` 原始轨迹 trajectory as supporting evidence. The Evaluator never loads the Subject's seed as its own running Session. Its initialization data uses `evalPrompt` as `userPrompt`, excludes the Subject's prompt, materials and initial Session, and maps the complete ordered `evalInitialMaterials` list to its own materials. The Harness sends the evaluation plan's JSON Schema through the dedicated `evaluationOutputSchema` initialization field; SP writes `/evaluation-output.schema.json` independently of Material roots. Its Submission sends `evalPrompt` followed by Eval's fixed evaluator instructions (`evaluatorPrompt()`): where the evidence is; with `results.submission`, call the `submit_evaluation` MCP tool directly with the evaluation ID and credential and finish with a short summary after acceptance; without it, write one JSON value following `/evaluation-output.schema.json` to `/output/result.json` and repeat that value in the final reply. SP submits that prompt unchanged. The SP initialization route is implemented in the independent SP service; this package keeps orchestration and does not access SP DO storage.

Execution and Evaluation share an `initialization` retry operation, separate from creation, submission, status, collection, resources, persistence, stop and restart. It retries the preparation callback against the same Agent with unchanged inputs and operation-specific idempotency keys, without creating another attempt, consuming restart capacity or inspecting an unsubmitted Submission. Retryability is checked before consulting the injected controller; unretryable errors and exhausted retries fail without submitting a task. The Runtime controller gives every idempotent operation except `restart` a fixed ten-retry budget with 250 ms initial backoff and a 10 s cap. Preparation is marked complete only after every step succeeds and is not repeated after an Agent restart.

After a Subject execution succeeds, Runtime calls `exportEvidence({handle, submissionId, limits})` and `EvidenceStore.resume()` to freeze an immutable, content-addressed evidence bundle: a `manifest.json` (`schemaVersion`, `evidenceId`, source, artifacts with size/media type/sha256, trajectory summary and `omitted` entries) plus blobs stored once per sha256 for every artifact, original Subject Material file and ordered raw trajectory part. `evidenceId` is `sha256:` of the canonical manifest without `evidenceId`. `applyEvidenceLimits` applies `DEFAULT_EVIDENCE_LIMITS` (95 MB per file, 500 MB total, 20,000 files, excluded `node_modules`/`.git`/`.cache`/`.next`/`.turbo`/`__pycache__` segments) in path order and records everything left out in `omitted`. The Sampling stores `evidence: EvidenceBundleRef` and its `trajectory` points into the bundle (`evidence:<evidenceId>/trajectory/`). Export runs only after the whole execution succeeded and uses the Runtime's fixed idempotent retry policy. When transient export or save retries are exhausted, existing artifacts and trajectory remain on a nonterminal Sampling with `execution.evidencePending`; recovery only retries evidence finalization and never submits or restarts the Agent. A non-retryable finalization error marks the Sampling failed. Failed executions get no bundle. Runtime owns the bundle format (`createEvidenceStore(blobStore)`); the app supplies only an `EvidenceBlobStore`, and `open(ref)` verifies the manifest sha256.

Evaluation requires `sampling.evidence`; otherwise it fails with "sampling has no evidence bundle". Evaluator `ensureAgent()` receives only `evaluationId` (required for, and only for, Evaluators; echoed as `AgentHandle.evaluationId`). Preparation first runs `materializeInitialData()`, then `importEvidence({handle, idempotencyKey: "evidence:<evidenceId>:<evaluationId>", evidence, root: "/evidence"})`, which writes `/evidence/artifacts/<original path>`, `/evidence/trajectory/events-000001.jsonl` 等有序分片 and finally `/evidence/manifest.json` into the Evaluator's own Space. The Evaluator cannot submit until import is confirmed. Repeated evaluations of one Sampling reuse the same bundle; the Subject is exported once. `collectEvaluation()` reads the legacy `structuredOutput` from `/output/result.json` in the Evaluator's own Space when no accepted MCP result exists; the result port checks an accepted submission first. Eval owns no DO storage or second preparation registry.

Each submitted execution/evaluation attempt owns a persisted `AgentResourceState`; the raw snapshot itself is stored apart from it (see [Attempt resource snapshots](#attempt-resource-snapshots)). Before dispatch, Runtime persists the pending operation scope as `chatId + idempotencyKey`; SP assigns the actual Submission ID on acceptance, which Runtime saves on the Attempt immediately after the receipt or recovery lookup. A collected resource snapshot must include `chatId + submissionId + idempotencyKey`; the Harness may resolve the operation by Chat and key if the receipt is uncertain. Runtime calls the required public `Harness.collectAgentResources()` after terminal observation or uncertain submission/status failure, before collecting outputs, deciding a restart or publishing the stage's terminal state. Creation/initialization failures that never dispatch have no resource collection. Failed, interrupted and cancelled submissions are collected too. Every restart keeps the previous attempt's facts; a separately requested evaluation keeps its own facts in its new EvaluationRecord. Store updates atomically persist the snapshot, attempt and its resource state with the owning Sampling/EvaluationRecord. No resource ledger, database client or DO storage access is added to Runtime.

SP supplies an operation-scoped, consistent snapshot containing only that operation's new work and descendants, excluding imported Session history and shared Subject evidence. `usageEvents`, `telemetryEvents` and `billingSettlements` contain the original JSON records: all fields, missing fields, null values, source identities, parent/child relationships, ordering and duplicates are retained. Runtime validates only the requested scope, collection envelope and lossless JSON serializability; it does not extract model requests/tools/Turns, normalize statuses/Token fields, merge events, deduplicate, calculate totals/durations, convert currencies or reprice billing. Source `coverage` and `finalized` metadata are preserved rather than used to derive a second resource-completeness result. Runtime stores no processed resource metrics.

Resource reads use the Runtime's fixed ten-retry budget and backoff; for downloads the count is saved on the Attempt before each one, so it survives a crashed process. Retry re-reads the same scope and never creates/restarts an Agent or resubmits work. `AgentResourceState.status` is only `pending | collected | failed`: collected means the original snapshot was saved, not that the source is complete. When the download budget is spent, a collected snapshot is kept and otherwise the Attempt is `failed`, both marked `exhausted` and no longer owed; the refresh reports it through `onError`, never resource payloads. SP's `readiness` diagnostic is required on every newly read snapshot and stored unchanged; stored historical snapshots may lack it. When an ended Agent (terminal Attempt, or an Evaluator whose MCP result was accepted) still owes a failed or unfinalized snapshot (`stageOwesResources`, the one definition shared with the API's resource recollection), its stage state carries `resourcesPending`, derived from and committed with the Attempt write. A finished stage with that flag gets read-only refresh passes on resume (same Chat, key and Submission; no ensure/submit/restart; stage status, output, evidence and accepted results unchanged), spaced by `nextAttemptAt` (60 s, never after `deadline`); at the deadline the current snapshot is kept, the flag cleared and the shortfall reported once. The flag never enters `PENDING_SAMPLING_STATUSES`; `isStageRecoveryPending()` lets a recovery store keep a Run without a pending stop scheduled. Finalizing a stop never reads resources: each ended Attempt still owing them without a collected snapshot is saved as `failed` (`Run stopped before resources were collected`), a collected snapshot is kept, and the flag is cleared; a later manual resource recollection refreshes them as usual. An unconfirmable terminal status persists `observationPending` across Worker passes; the next pass re-observes the same Attempt and Submission, only an explicit failed/interrupted/cancelled terminal consumes `maxRestarts`, and after `OBSERVATION_MAX_ATTEMPTS` passes the stage fails with an explicit message. Status errors carry the inspection outcome (`inspect: null` / `inspect error: …`). Resource collection does not change the Agent/output result or replace its original error. `getSampling()` and EvaluationRecord queries expose these durable facts even from a new Runtime instance; Metrics consumes the application's `MetricsSource` facts rather than SP or private Store tables. Artifacts and complete trajectories still use references; resource snapshots store source resource events, not an additional Workspace or Session copy. Subject artifacts and the complete trajectory are required: after a terminal Submission, execution stays nonterminal until both references and the final execution status are saved together. `execution.evidencePending` marks evidence finalization for recovery without submitting or restarting the Agent; the original Agent failure is preserved.

Agent terminal facts are captured immediately on observation, before resource collection or persistence. The terminal Attempt is saved before resource collection so a later resource write failure cannot erase the already-observed Agent result. The same terminal status and completion time are retained through all subsequent errors. A completed Attempt never becomes failed because Runtime finalization failed; the owning execution/evaluation stage's `lastError` records that separate failure. Record writes use the Runtime's fixed ten-retry budget and backoff: the expected immutable record is captured once, a failed write is reconciled against the latest stored facts, and any retry saves the same record without collecting resources/output again or creating, submitting or restarting an Agent. Writes compare and bump the record's Store `revision`; reconciliation compares JSON facts without depending on object property order, while retaining array ordering, duplicates and null values. The same stage RetryController is shared by lifecycle and persistence rather than allocating a fresh allowance for each write. This applies to resource records, terminal Attempt facts, output saves and cancellation/error finalization, not Run admission.

Pipeline cancellation writes for failed executions run independently of the successful Samplings' evaluation scheduler. Each cancellation reconciles/retries only its own EvaluationRecord. If cancellation cannot be saved, its finalization error is recorded on that EvaluationRecord, never on another Sampling, and already-confirmed cancellation is not downgraded. Successful Samplings do not wait for unrelated cancellation retries. If even the local error record cannot be persisted, `EvalRunResumerDependencies.onError` receives a scoped Error (console error reporting is the default); there is no silent discard or global failure rewrite caused by an unrelated cancellation. No new Run state, version, operation registry or orchestration entity is added.

Every Runtime Sampling/Evaluation update carries the previous persisted facts as its expected value. A Store atomically replaces a record only while those facts still match. A changed record is read and reconciled, never overwritten by an old full-record snapshot. This conditional write adds no persisted version. If write and read-back both fail until the persistence budget is exhausted, Runtime treats the commit outcome as unknown and leaves the stage recoverable; lifecycle error handling cannot write a failure status from stale memory. A collected resource snapshot remains intact when a later refresh fails, with the refresh error reported separately. Finalized snapshots are not refreshed. Resource refresh passes on a finished stage use the same conditional write, so a failed pass never replaces a saved snapshot.

### `eval-metrics`

Numeric observations share one population-variance implementation with only nonmissing N in the denominator. Resource distribution observations are per Subject/Evaluator Agent, interpreted from that Agent's original Attempts by the same resource interpreter; operation lengths/durations are per call and Schema numbers per field observation. The interpreter determines group attribution independently of numeric availability: a complete source can prove an unused group is zero even when other groups lack numbers, while potentially matching unattributed records prevent that proof. Scope totals still deduplicate all raw events directly; no scope averages are averaged again. The Metrics resource projection also owns cache hit rate (`cacheRead / (input + cacheRead)`) and preserves the weaker source coverage. Public `AggregatedResourceStatistics` adds these per-Agent distributions to the resource totals, while an individual `AgentMetricView` keeps its own resource facts.

Owns three internal submodules: `evaluators` compiles the Project Schema into one presentation plan, validates EvaluationRecord outputs and produces observations from matching declarations; `aggregation` computes resources, trajectories, Agent views and field statistics; `reporting` serves Project → Dataset → ProjectSample → Sampling views. The plan retains declaration provenance, real array coordinates, conditional guards and the root Schema's reference/dynamic-anchor context, reusing Ajv's registered validators and resolver. Its public field definitions provide titles, descriptions, kinds, options and nullability; they are derived, never independently configured or persisted. Display unions never confer observation eligibility. Each record is interpreted once; detail and aggregation consume the same complete facts, retaining null-only facts until scope selection. Field coverage requires actual observations and every queried evaluation contributing for completeness. There is no independent evaluator execution or attribution workflow. It reads original Project-plan/Runtime facts, including failed/cancelled/restarted work, without querying SP or repricing bills. Resource interpretation, source-identity deduplication, parent/child overlap handling, model/Token normalization, cache hit rate, costs, trajectory/tool/request/Turn counts, durations, success rates, Schema validation and all higher-level summaries belong here, not in Runtime.

`MetricsSource.read(query)` is the application's read-only, consistent projection port, not another Store. Its `MetricsFacts` contain the `ProjectPlan`, the evaluation-plan Schema content (or null), every bound ProjectSample in the queried scope including never-run ones, the current Samplings and EvaluationRecords, and the relevant Run snapshots. The package does not access private Store tables or implement PostgreSQL/DO/R2 adapters. Source results are detached and validated before processing. Every view requires an explicit Project scope. The hierarchy comes only from the Project snapshot, never the live catalog: a ProjectSample without Samplings still appears with null/unavailable values, and a shared ProjectSample appears under each bound Dataset while Project totals deduplicate by Sampling and Evaluation identity. Every level is recomputed from the underlying raw records, never by averaging child summaries. The default query reads the Project's current result set; optional `runIds` restrict only Sampling and Evaluation records, not the fixed bindings.

Each `MetricSummary` keeps the Subject (`executionAgent`) and Evaluator (`evaluationAgents`) resources apart, and `getSamplingDetail` returns an `AgentMetricView` for the Subject and each Evaluator plus an `EvaluationOutputView` per evaluation (raw text, parsed JSON, validation, field observations, artifacts, evidence and trajectory references). Trajectory metrics come from each Attempt's stored SP telemetry events merged across Attempts: Turn counts and outcomes, per-tool counts, outcomes, durations and input/output UTF-8 byte lengths (missing or redacted bodies are counted as missing, never zero), model Steps counted by `generation` operation, thinking Steps whose own or owning Turn output has a thinking/signature marker, content Steps whose own or owning Turn output has a content marker, and generation tokens attributed to the matching Step; a Turn may contain several Steps, a Step may belong to both categories, and tool operations remain a separate operation count. An unlinked generation with its own marker is still classified as a Step and retains an unlinked diagnostic, but its category coverage is partial; an unlinked generation without its own marker cannot prove the related category and yields partial/unavailable rather than subtraction. Output fields are extracted only from successful, Schema-valid outputs at fields the Schema declares `number`/`integer`, `boolean` or `enum`/`const` (an enum array is the enum at its `*` item pointer), keyed by JSON Pointer with array indexes as `*`, through one Schema walk that intersects a node with its `$ref` and `allOf` members and unites `anyOf`/`oneOf`/`then`/`else` alternatives; a field's shape is its declared shape united with the Schema locations outputs actually reach (map keys, `patternProperties`, recursion). Each field reports its kinds, observation, contributing and missing evaluation counts, a numeric summary over numbers only, a distribution of boolean/enum entries in Schema order with occurrence count, evaluations containing the value and share of all observed values, and coverage. A null the Schema allows is counted separately in `nullCount` (present only when the Schema allows null), never in the distribution and never a number, false, an enum value or a missing evaluation; free-text strings and objects are not aggregated. The field rules live in the package README. Without an evaluation plan output fields are unavailable while execution metrics still show. A failed Agent, a Runtime finalization error and a missing or invalid output remain different facts and are never zero. Stage success rates use terminal records as the denominator; durations describe Agent and Attempt spans, not a batch's parallel wall-clock time.

Resource totals carry `complete | partial | unavailable` coverage and nullable values. Complete empty source streams can prove zero; absent, pending, failed, unfinalized or unsupported data cannot. Usage identity is owner plus eventId, telemetry identity is session plus eventId, operation identity is session plus operationId, and model settlement identity is accountId plus eventId. Missing source identities or contradictory duplicates are diagnosed rather than silently counted. Action charges use their execution identity. Provider USD, model debits, rated/shortfall/platform-owned units and actual Action charges stay separate; the package does not derive charges from prices or tool estimates. A Subagent summary suppresses child detail only for each individual Token or Provider USD metric that contains a valid value; missing summary metrics keep valid child detail and report the resulting coverage. Actual distinct billing settlements remain authoritative charges. SP input/output/cache buckets are disjoint, while reasoning is an output subset and is not added to total tokens. Model requests and Turns are counted from distinct telemetry operations, not usage rows or model-request/Turn equivalence. Per-tool outcomes and durations come from paired start/terminal events; `inProgress` is reserved for operations belonging to an active Attempt, while an unclosed operation from a terminal Attempt is `unknown`. Parsing does not mutate any raw source records.

The recognized billing facts are SP's model settlement receipt with its authoritative `accountId` and public Action log entries using `executionId` and `chargedCredits`. An in-progress Action is not a settlement, even if its provisional charged field is zero. Unsupported statuses and private database row layouts are not reinterpreted as final charges. The resource carrier still preserves those original records for diagnostics.

Ambiguous subagent summaries and cyclic parent relationships are diagnosed and cannot suppress trustworthy child details. Contradictory terminal outcomes or tool names remain unknown instead of picking a winner. Binding counts (Datasets, Data, ProjectSamples) describe the Project snapshot, including Data without runs.

The file layout lives in [packages/eval-metrics/README.md](../packages/eval-metrics/README.md). The root entry exports `createMetrics`, the error classes (`MetricsEntityNotFoundError` for an unknown Project, Run, Dataset, ProjectSample or Sampling, `MetricsQueryError`, `MetricsSourceError`), the model types and the bounded telemetry projection helpers used by the API persistence adapter. Experiment comparison, metric persistence/caches and application UIs are not introduced.

### `apps/eval-api`

The application owns the database migration command used locally and by deployment. It validates the recorded Drizzle migration history against the checked-in SQL before applying pending migrations, then verifies that the application's table and column projection is readable. A changed applied migration or missing schema fails deployment before the API/Worker image is replaced; this command never resets a database or adds runtime compatibility with an older schema.

Deployment smoke checks authenticate and read all four data catalogs. Demonstration fixtures use public HTTP upload contracts and never insert database rows or produce synthetic execution results; they are not part of deployment or application startup.

Internal control-plane composition boundary. Its authenticated HTTP API is specified in [Eval HTTP control plane](eval-http-api.md): every request is scoped to one fixed Eval SP service account, whose long-lived session is verified with Eval SP at startup, and composes only that account's Agent Config, Project, Dataset, Run admission, observation and Metrics services. The Run admission endpoints persist work for the separate Worker; they do not run Agents in the HTTP process. Its PostgreSQL adapters implement the public `DatasetStore`, `ProjectPlanReader` and `RuntimeStore` ports, and one read-only `MetricsSource` over a consistent snapshot. The adapters share a caller-injected Drizzle/`pg` connection; the application does not import SP private database code or read Durable Object storage. Database constraints, not process memory, enforce same-owner Dataset/Data, Project/ProjectSample/Sampling/Evaluation and Run membership relationships, atomic Dataset imports and Project-scoped Run idempotency uniqueness. Run views are read through one owner- and Project-scoped, consistent snapshot: the adapter fetches the Run and its Sampling/Evaluation facts in sets, then uses the public Runtime projection for status, never saved as a second status.

Project Schema viewing uses the same plan-bound ID and digest reader as Worker and Metrics. The public `EvaluationOutputSchemaDocument` returns its reference and content together; catalog soft deletes do not affect existing Project reads. Project ownership and visibility are checked in that same read snapshot. The catalog still excludes deleted records from new selections.

Project creation snapshots the selected Datasets and Data in one consistent read (one ProjectSample per distinct Data), freezes the Subject Agent Config (and the Evaluator one when an evaluation plan is supplied) as SP copies, persists the snapshot, both plans and the copy rows in one transaction, then admits the first execution or pipeline Run under the creation `idempotencyKey`; replay, race and compensation rules are defined in [Project 创建](eval-project-redesign.md#31-创建). `PUT /api/projects/:id/evaluation-plan` replaces an unlocked evaluation plan as a whole, freezing a new Evaluator copy and discarding the previous one; it shares the Project row lock with admission and conflicts once the plan is locked. There is no other Project write path besides soft deletion, which is rejected while a Run is unfinished. `/api/agent-configs` is the Eval-side CRUD over the Eval SP `user-agent` library: frozen copies are hidden from its lists and refuse edits and deletion. Run admission exposes `preview` and `submit` over the Project snapshot; the selection and submission contract for evaluation-only Runs is in [Evaluation-only Run entry](eval-independent-evaluation-entry.md), and replacement and the superseded-key rule follow [Run admission](architecture.md#run-准入与独立评估). Observation endpoints resolve an `AgentObservationRef` for a current Sampling or Evaluation of a non-deleted Project in any Run state.

The application also owns the Node Run Worker, not a fifth package. Run admission and stop requests enqueue a pg-boss job in the same PostgreSQL transaction as the Run facts; Worker instances consume it and invoke Runtime `resume(runId)`, which reads the Project plan and checks the Run's plan digests. `createEvalRunResumer` exposes only recovery and requires an all-owner `ProjectPlanReader`, Store, Harness and `EvidenceStore` (optional `evidenceLimits`; the SP Worker passes `spEvidenceLimits(DEFAULT_EVIDENCE_LIMITS)`); admission stays in the API control plane. pg-boss owns the job table; no duplicate Run status is added. A Run waiting only for resource checks is woken by a delayed job at its earliest `nextAttemptAt` rather than by retry backoff. The PostgreSQL Run activeness query is the SQL form of `isStageRecoveryPending()` from `eval-contracts` (plus stop and Run-ownership rules); a persistence test checks both on the same stage fixtures. Several Worker instances may run at once; scheduling, recovery and its remaining risks are recorded in [Run scheduling and stop](architecture.md#run-调度与停止). The Eval-side SP Harness calls the public routes implemented on the independent SP branch; real cross-deployment verification remains.

Projects have an ownerUserId and bind the deployed SP Git branch. Dataset and Data are owned by one Eval SP user; Data is reusable across that user's datasets, never across owners, and Projects hold their own copies. The application Store must scope every user-facing read, write, import and association to the authenticated user and enforce same-owner references in PostgreSQL. ProjectSample, Sampling, Evaluation and Run rows carry the same owner as their Project through composite foreign keys. Every Run has one required `idempotencyKey` and request fingerprint, unique within its Project; another Project may use the same key. The Worker Store remains global and does not interpret these keys without a Run owner. The user-facing `ProjectPlanReader`, RuntimeStore and `MetricsSource` require the fixed service account identity that Eval SP verifies at startup and apply it in SQL. A separate Worker RuntimeStore and plan reader can resume any user's Run and must never be exposed through HTTP. `MetricsSource` limits reads to the requested Project and optionally selected Runs, limits both Sampling and Evaluation records, and reads under a single repeatable-read, read-only transaction. Eval SP owns the service account and its `user-agent` library; Eval stores frozen-copy references, their display snapshots and the copy-to-Project mapping, never an editable Agent Config. The concrete public SP HTTP/WebSocket client belongs to this application composition layer, not a fifth shared package.

## SP alignment

The runtime Harness must consume the same public concepts as `sp-platform`:

- Agent Config reference in the independent Eval SP `user-agent` library: `ownerUserId`, `userAgentId`;
- ordinary Inbox/Chat ensure in the independent Eval SP deployment, with `evaluationId` for Evaluators; these Chats do not appear in dev/production Inbox;
- evidence export (artifact list, file bytes, trajectory pages) from a terminal Chat and evidence file import into an Evaluator's own Space;
- `dispatchMessage(message, "enqueue" | "steer")`;
- `SubmissionReceipt` and `getSubmission()`;
- `TrajectoryPage` pagination with SP's maximum page size;
- Workspace tree, manifests and content boundaries.

Runtime records a preassigned Chat ID on Sampling/EvaluationRecord and the actual per-attempt Submission ID on each Attempt. The concrete SP Harness returns the real Submission ID from SP receipts and inspects uncertain operations by Chat and key; Runtime persists the result on each Attempt.

The Eval UI reaches Chats through Sampling/Evaluation observation references rather than an Inbox management screen. Viewing Context, Workspace and Trajectory is read-only for interactive users; only the controlled Run Worker submits work. The independent SP branch implements unattended decisions, evidence export/import routes and operation-scoped resource reads. SP returns the Evaluator's raw `structuredOutput` from its own Space; it still has to enforce read-only observation server-side; see [SP requirements](sp-eval-api-requirements.md). Eval Web's read-only views still require integration and cross-deployment verification.

The Chat ID is assigned before provisioning and reused after an uncertain creation response. `ensureAgent` retries retain the same creation facts and Chat ID; a separately requested re-evaluation receives a new Evaluator Chat and EvaluationRecord identity. Chat creation identity is distinct from the idempotency key used to submit or restart work inside that Chat.

The eval project must not import SP private source files, use Web projections as facts, or read Durable Object SQLite directly.

### Bounded Metrics reads

`eval-metrics` owns the deterministic compact telemetry projection (`compactResourceSnapshot`): source-event SHA-256, event/operation identity, status/time/Token fields, canonical input/output byte lengths and versioned thinking/content marker flags. It preserves per-event observations for exact medians, cross-Attempt deduplication and conflicts; it is not an average of lower-level summaries.

### Attempt resource snapshots

An Attempt's raw SP resource snapshot (every usage, telemetry and billing event unchanged, including full prompts and tool bodies) is stored once, outside its stage record, in the same transaction as the compare-and-set write that marks it collected (`RuntimeStore.updateSampling`/`updateEvaluation` with `resources`), so a conflict stores neither and the snapshot never diverges from its summary. Stage facts keep only `AgentResourceState`: status, scope or a summary (scope, observedAt, finalized, coverage, readiness, event counts), the download count and whether Runtime gave up. Scheduling, status, stop, Run views and every stage write therefore never load or rewrite snapshot bodies. `eval-api` stores each snapshot in `eval_attempt_resources` (key: stage, record ID, Attempt ID; rows go with their Sampling/Evaluation) together with its compact projection, written in the same statement; Metrics attaches those projections one record at a time as `MetricsSampling`/`MetricsEvaluation`, and Sampling detail returns the stored records without them; one Attempt's raw snapshot is downloadable on its own, streamed from PostgreSQL without parsing. Stage records are written by compare-and-set on a per-record `revision`, never by comparing stored facts.

The lifecycle and finished-stage refresh share `collectResources()` for budget admission, readiness, downloads and give-up reporting. It checks the persisted download budget before any resource read. Each download is counted after acquiring the process-wide slot and before starting HTTP, so a crashed download consumes the same `resources` retry budget but a cancelled queued task does not. The slot covers count persistence (including CAS retries), the physical request/body read and atomic snapshot save; readiness waits and download backoff stay outside it. Resource Harness inputs accept a non-persisted `signal?: AbortSignal` and settle only after request/body cancellation or completion; racing an observer must not release the slot. Once the budget is spent the Attempt is given up (`failed`, or its collected snapshot kept, with `exhausted`), Runtime no longer owes it, the stage status is unchanged and the Run can finish. The shared flow reports through `onError` after saving exhausted state; later recovery does not repeat the report, though a crash between save and callback can lose it. A manual resource recollection gives a fresh budget. Snapshots are validated in place, never copied.

After budget admission, resource refresh uses the shared flow's optional internal `prepare` step to confirm and persist an accepted Evaluator's missing terminal receipt before resource reads or a finalized-snapshot return. A failed terminal write leaves its durable recovery entry intact. An already finalized snapshot needs no readiness read or download; an exhausted budget performs no receipt read. Preparation is not repeated for download retries.

MCP-enabled Evaluations complete on validated result acceptance, atomically with the result and its revision. Status-socket loss is recoverable observation failure, not an Evaluation terminal fact. Late submissions cannot bypass Project deletion, Run stop/cancellation or replacement. Runtime preserves accepted results when subsequent observation or collection fails. See [evaluation result submission](eval-evaluation-result-submission.md).

Runtime owns one narrow completed-Evaluator recovery: when no result was submitted and that Submission's final reply contains `Dynamic worker concurrency limit exceeded`, the existing `restart` operation may start another Attempt under the evaluation plan's `maxRestarts` and normal backoff (default: four restarts, five total Attempts). It shares the same persisted Attempt count as failed Submissions, not an additional retry allowance. It continues the same Evaluator Chat with a new idempotent operation key, without reinitializing, importing evidence again or rerunning the Subject. The completed Attempt keeps its terminal facts and resources and records the exact recovery reason in `error`. Accepted or invalid results, unrelated missing results, manual recollection and stopped Runs never trigger it. MCP acceptance is checked again before the restart decision; final replies supply diagnostics only, never substitute for MCP acceptance.
