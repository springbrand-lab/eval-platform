# Package Boundaries

## Repository layout

```text
eval-platform/
├── packages/
│   ├── eval-contracts/
│   ├── eval-dataset/
│   ├── eval-runtime/
│   └── eval-metrics/
└── apps/
    ├── eval-api/
    ├── eval-web/
    └── eval-cli/
```

The four package workspaces keep the package boundary stable. `eval-runtime` contains runtime orchestration; `eval-dataset` contains Dataset/Data management, validation and serialization. Persistence implementations and application integration remain outside these package cores. Applications additionally contain `CONTEXT.md`.

The deployment source for the SP Harness is a fixed SP Git branch resolved to a commit during one Eval release workflow. That workflow deploys an independent Eval SP API/database, Agent Worker, Space Worker, DO namespaces and R2; all Eval SP calls, including login and Agent Config, target this deployment. Deployment orchestration is repository-level work, not another workspace package. See [Eval SP deployment](eval-sp-deployment.md). The source branch belongs to Project, while each Run records the actual source commit; Sampling does not own a branch.

Package-internal submodules:

```text
eval-dataset/
└── dataset/

eval-runtime/
├── config/
├── harness/
└── runtime/

eval-metrics/
├── evaluators/
├── aggregation/
└── reporting/
```

## Dependency direction

```text
eval-contracts → eval-dataset → eval-runtime → eval-metrics
                        ↓             ↓             ↓
                       eval-api / eval-web / eval-cli
```

The arrows describe allowed consumption direction. The contract package must not depend on runtime, storage, API, Web, CLI or Cloudflare bindings; only its `./http-errors` and `./http` subpaths depend on `@springbrand/http` and `hono`.

## Package responsibilities

### `eval-contracts`

Owns stable runtime/evaluation types shared across packages: Project, Sampling, HarnessConfig, ExecutionOutput, EvaluationAgentOutput, ArtifactRef, TrajectoryRef and EvidenceRef. Project binds the selected deployment's SP source branch and records its first admitted execution or pipeline Run's operation/configuration choice. Later execution or pipeline Runs must use that same choice; independent evaluation adds another Run in the same Project without changing it. Run records the deployed source commit at admission as provenance, without adding a branch to Sampling. Dataset/Data belong to `eval-dataset`; runtime Sample belongs to `eval-runtime`. Evidence and explanations remain Evaluation Agent outputs, not an independent attribution contract. The status vocabularies (`SAMPLING_STATUSES`, `PENDING_SAMPLING_STATUSES`, `AGENT_STATUSES`, `TERMINAL_AGENT_STATUSES` and their predicates) are defined only here; SQL uses the same constants. `AgentSubmission.status` is SP's normalized status; SP's raw status is mapped once in the Harness adapter. The Eval API error-code catalog (`./http-errors`, built with `defineErrorCatalog`) and its Hono responders (`./http`) also live here; the HTTP contract is in [Eval HTTP control plane](eval-http-api.md).

An owner-scoped output-format catalog holds standalone named draft 2020-12 JSON Schema files; Project stores only the selected output-format ID. The selected ID may change until the first Evaluation Run is admitted, then becomes immutable. Every Evaluation Run requires it. Runtime resolves the Schema by ID, and every Evaluation Agent receives `evaluation-output.schema.json` below the initialization material root returned by SP in its confined Workspace before submission.

It is the only place for cross-package evaluation contracts. `AgentResourceSnapshot` carries unchanged SP usage events, telemetry events and billing settlements with collection scope and source-completeness metadata. It does not implement orchestration, persistence, normalization, aggregation or pricing.

### `eval-dataset`

Owns Dataset/Data schemas, required current `userPrompt`, optional per-Data `evalPrompt`, arbitrary additional JSON business fields, initial-session references, separate Subject `initialMaterials` and Evaluator `evalInitialMaterials` references, JSON/YAML serialization, strict prompt JSON/JSONL upload parsing and `createDatasetService(store)`. Dataset and Data are scoped to one Eval SP user by the application Store; Data is reusable across that user's datasets through explicit associations, not per-dataset copies. Runtime Sample is owned by `eval-runtime` and inherits its Data owner's scope. The pure Dataset package does not authenticate users or store SP accounts. Dataset and reference objects are strict; Data preserves arbitrary extra JSON business fields while validating known fields. Both prompts preserve their original text and reject blank values when supplied. `userPrompt` is required for Subject execution; `evalPrompt` is required when an Evaluation or Pipeline Run is admitted, while execution-only Data need not provide it. Prompt import also requires `evalPrompt`, `name` and `description` on every row and Dataset `description` alongside the file; the application Store persists an internal Prompt Dataset kind and preserves those requirements on later updates and membership changes. Extension fields cannot override the generated `dataId` on creation.

JSON numbers must be finite, and integers must stay within JavaScript's safe-integer range at every input, persistence validation and serialization boundary. Larger integer identities must be supplied as strings; the package rejects them rather than coercing or rounding them. YAML integers are parsed as BigInt and range-checked before conversion. JSON and YAML reject duplicate property names within each object; JSON checks decoded property names before native parsing can discard earlier values and does not accept JSONC extensions.

`InitialSessionRef` contains required `bundleId` and `sessionId`; `InitialMaterialsRef` contains required `bundleId` and `materialId`. Both references are optional and identify a resource within a Bundle rather than the Bundle alone. A material reference must resolve to uploaded files before initialization. Reference IDs are platform UUIDs validated by `platformIdSchema` and canonicalized to lowercase; the Dataset package does not generate or infer references. The Eval API's owner-scoped resource catalog generates Bundle/Material/Session UUIDs when users upload resources. Generator specs and inline resource bodies are not accepted as references. The initialization Session identity is not the active Chat/Submission identity. Eval's owner-scoped Bundle directory holds canonical Session JSON/JSONL; SP owns importing supplied context into the Chat Session, framework-native formats, tool-call schemas and Context reconstruction. The current task is the required `userPrompt`, not a field inferred from generic data or Session history. Dataset does not own a second Session store.

The internal files are `dataset/model.ts`, `dataset/input.ts`, `dataset/serialization.ts`, `dataset/store.ts` and `dataset/index.ts`; the package exposes only its root entry. Every user-input failure becomes `DatasetInputError`, and `parseStrictJson` is the single duplicate-key-rejecting JSON parser shared with the Eval API. Creation uses native UUIDs; editable-field updates are full replacements. Every platform UUID (Dataset, Data, Bundle, Material, Session, output format) is validated by the one exported `platformIdSchema` and canonicalized to lowercase, following SP's Zod UUID normalization pattern. Import, duplicate detection, service queries, Store comparisons and returned snapshots use that canonical identity. Resource reference IDs use the same canonical form so catalog lookup, Bundle file resolution and deletion checks agree; Data business fields remain unchanged. Serialization has no persistence side effects. Import assigns missing IDs and submits a complete `DatasetSnapshot` through one atomic Store command. Existing IDs may be reused only for identical content; conflicting imports never overwrite or partially commit. Deleting a Dataset preserves shared Data; deleting referenced Data is rejected atomically. Export reads one consistent Store snapshot.

`DatasetStore` is the application-injected PostgreSQL persistence port. Its implementation must follow SP's transaction, uniqueness and foreign-key constraint pattern, not instantiate a database client inside the Dataset package or rely on service-side prechecks. It validates owner-scoped active Material/Session references in every Data write path, including general create, update and import; a soft-deleted resource cannot be newly referenced. Catalog deletion is blocked while Data or Project binds the resource and otherwise uses a `deleted_at` marker, consistent with SP's soft-delete pattern. File bundles remain references to existing material capabilities; the package does not generate manifests/hashes, upload/download files, own an R2 binding or operate DO storage. Runtime/Harness owns materialization through public Workspace boundaries. SP's private workspace helpers are not copied or imported across repository source paths.

### `eval-runtime`

The API process can construct an admission-only Runtime interface without a Harness credential; only the Worker constructs the resume interface with a real Harness. Both entries use the same request identity and Store implementation.

Owns Config resolution plus `start`, `evaluate`, `pipeline`, `getRun`, `getSampling`, `getEvaluation`, `listEvaluations`, Sampling lifecycle, separate execution/evaluation concurrency limits, retry, evaluation-input materialization and the `RuntimeStore` persistence port. `ExecutionConfig` owns Dataset/Sample selection and Subject execution policy; `EvaluationConfig` owns the Evaluation Agent policy; `PipelineConfig` composes the two. Runtime requests only select these configs and provide the Project/Sampling scope required by the operation. `ConfigResolver` is the single runtime parsing/validation/normalization boundary and returns effective configs with explicit defaults. `RuntimeStore.createRunWithSamplings()` atomically creates the Run, Sampling records, the Run's EvaluationRecords and the Run's immutable effective-config snapshot; the Runtime does not sequence independent persistence calls for one aggregate. Run status is a derived query projection from Sampling and EvaluationRecord state, not a separately persisted RuntimeStore field. No config version concept is introduced. SP is the first-party Harness contract inside this boundary; `apps/eval-api` composes its concrete public HTTP/WebSocket client, and a separate `eval-sp-adapter` package is intentionally not created.

Run binds a batch of Samplings to an immutable scope of actual phases: execution, evaluation, or execution followed by evaluation. `RunPhase` contains only `execution | evaluation`; `RunPhases` allows only those three valid scopes. A Run is the same generic query handle for each scope, not a separate Pipeline entity or Run kind. `getRun()` derives both the current phase and status from the scoped Sampling states. `pipeline()` only sequences the two real phases, and failure handling follows the next unfinished phase without a Pipeline-specific state branch.

Harness exposes `ensureAgent`, not an unconditional creation operation. SP Chat is the persistent Session; each prompt submission within that Chat has its own SP Submission ID. Runtime assigns and persists the Subject `subjectChatId` or Evaluator `chatId` before calling SP, then passes it through the ordinary Inbox/Chat creation seam of the independent Eval SP deployment. Repeated or concurrent ensures for the same Chat identity must return the original Agent handle. An identity already bound to a different owner, Project, Sampling, role, framework, Agent Config or Evaluator Workspace binding must fail without rebinding or creating another Agent. SP owns authoritative deduplication and provisioning; Runtime owns identity persistence and operation-specific retry decisions, not a second local creation registry.

`start()`, `pipeline()` and `evaluate()` share one Run-admission rule: a Project-scoped `idempotencyKey`, at most one unfinished Run per Project, and atomic replacement of prior Project state; the Store, not Runtime memory, is the source of truth. The complete rule is described once in [Run admission](architecture.md#run-准入与独立评估).

Project stop is owned by `eval-runtime` through the `withRunDispatchGate()` Store port and `stop()`; its lifecycle is described once in [Run scheduling and stop](architecture.md#run-调度与停止).

Static Sample input belongs to the Catalog, not to each Sampling record. `SamplingState` contains only run-specific Sampling state; `EvaluationRecord` independently owns evaluator, submission, attempts, status and output, linked by `samplingId`. Execution consumes a temporary `RuntimeSamplingContext`; evaluation consumes a temporary `RuntimeEvaluationContext` that joins Sampling, EvaluationRecord and Sample. Store commands never include those temporary contexts, and `getSampling()` returns a separate flat `SamplingSnapshot`. Independent evaluation reads selected Sampling states through owner-scoped `RuntimeStore.getSamplings()` and distinct Sample inputs through `RuntimeCatalog.getSamples()` in bounded SQL batches before the atomic Run/Sampling/EvaluationRecord write; recovery likewise reads EvaluationRecords through `RuntimeStore.getEvaluations()`. Batch ports preserve caller order and report missing items as null. No Sample versions or input snapshots are introduced.

`Sample` is `{ sampleId: string, data: Data }`, not an extension of Data. Catalog methods and Runtime input preparation consume this single shape, with no flattened compatibility branch. The outer `sampleId` is a platform identity; a business `sampleId` inside Data remains arbitrary JSON and is preserved for both Subject and Evaluation Agent initialization. Only Data's platform `dataId` is stripped from the Agent input. This does not introduce a persisted Data copy for each Sampling.

`HarnessConfig.kind` selects the SP hosting boundary, while its required `framework` selects the Subject engine: `sp`, `codex`, or `cc` (Claude Code). All three use the same public Chat/Submission/Workspace lifecycle, not an eval-owned CLI or process launcher. `EvaluationConfig` requires the SP framework and a selected SP Agent Config. The framework is part of the Run's effective-config snapshot, request fingerprint and immutable Agent creation facts. `ensureAgent` receives it and returns a handle bound to that framework; subsequent operations use that handle, and retries cannot silently switch engines. Missing or unsupported frameworks fail configuration validation without falling back to SP. The eval-side boundary assumes SP provisions the selected engine; this change does not implement cloud provisioning in SP.

Before a Subject's first submission, `materializeInitialData()` receives Data's business fields except `evalPrompt`, `evalInitialMaterials` and platform Sample/Data identities. Eval resolves the Subject's `initialMaterials` reference to file bytes and sends them through the SP initialization route; SP writes them to the target Chat Workspace. When an optional canonical Session context file exists, SP imports it into that Chat Session before the first Submission. Without a context file, Eval passes the Session reference without importing history. The current `userPrompt` is then submitted unchanged, not wrapped with business data or Session history. Its stable initialization idempotency key is scoped to the target Chat/Session identity; repeated calls return the original preparation result without restoring over an advanced Session, and conflicting initialization facts are rejected. Runtime stores no second preparation registry. A restart continues the existing Agent Session and does not reapply the seed. Session references and bodies are not included in the execution prompt or Sampling persistence. An Evaluation Agent remains an independent Chat and Session, but its Workspace is bound to the Subject Chat's physical SpaceDO by the Subject owner user ID and Chat ID. Its own material inputs and outputs are confined to `/evaluations/<evaluationId>/`; Subject artifacts remain in place and are read as primary evidence. The complete Subject trajectory is materialized into that same SpaceDO as supporting evidence. The Evaluator never loads the Subject's seed as its own running Session. Its initialization data uses `evalPrompt` as `userPrompt`, excludes the Subject's prompt, materials and initial Session, and maps `evalInitialMaterials` to its own material reference. The Harness adds the Project JSON Schema as `evaluation-output.schema.json` under the returned material root in the same initialization payload, rejecting a colliding material path. Its Submission sends `evalPrompt` unchanged instead of a generated instruction. The SP initialization route is implemented in the independent SP service; this package keeps orchestration and does not access SP DO storage.

Execution and Evaluation share an `initialization` retry operation, separate from creation, submission, status, collection and restart. It retries the preparation callback against the same Agent with unchanged inputs and operation-specific idempotency keys, without creating another attempt, consuming restart capacity or inspecting an unsubmitted Submission. Retryability is checked before consulting the injected controller; unretryable errors and exhausted retries fail without submitting a task. The default controller deliberately leaves initialization counts and backoff unspecified, as it does for other non-restart operations. Preparation is marked complete only after every step succeeds and is not repeated after an Agent restart.

Evaluator `ensureAgent()` receives an immutable `evaluationWorkspace` binding containing the Subject's `{userId, chatId}` and the target `evaluationId`; retrying with conflicting binding facts fails. SP creates the Subject Chat under its selected `AgentConfigRef.ownerUserId`, which supplies the SpaceDO `userId` when a later independent Evaluation reconstructs the binding. `materializeSubjectTrajectory()` receives that Subject Workspace reference, the collected complete `TrajectoryRef` and the stable `subject-trajectory:<subjectChatId>` idempotency key. SP reads the Subject Chat's trajectory and writes it once to its own SpaceDO; repeated evaluations reuse the same file. The preparation callback may be retried after a lost response, but the Evaluator cannot submit until SP confirms materialization. No Subject artifact bytes are copied, and Eval owns no DO storage or second preparation registry.

Each submitted execution/evaluation attempt owns a persisted `AgentResourceCollection`. Before dispatch, Runtime persists the pending operation scope as `chatId + idempotencyKey`; SP assigns the actual Submission ID on acceptance, which Runtime saves on the Attempt immediately after the receipt or recovery lookup. A collected resource snapshot must include `chatId + submissionId + idempotencyKey`; the Harness may resolve the operation by Chat and key if the receipt is uncertain. Runtime calls the required public `Harness.collectAgentResources()` after terminal observation or uncertain submission/status failure, before collecting outputs, deciding a restart or publishing the stage's terminal state. Creation/initialization failures that never dispatch have no resource collection. Failed, interrupted and cancelled submissions are collected too. Every restart keeps the previous attempt's facts; a separately requested evaluation keeps its own facts in its new EvaluationRecord. Store updates atomically persist the attempt and its resource collection with the owning Sampling/EvaluationRecord. No resource ledger, database client or DO storage access is added to Runtime.

SP supplies an operation-scoped, consistent snapshot containing only that operation's new work and descendants, excluding imported Session history and shared Subject evidence. `usageEvents`, `telemetryEvents` and `billingSettlements` contain the original JSON records: all fields, missing fields, null values, source identities, parent/child relationships, ordering and duplicates are retained. Runtime validates only the requested scope, collection envelope and lossless JSON serializability; it does not extract model requests/tools/Turns, normalize statuses/Token fields, merge events, deduplicate, calculate totals/durations, convert currencies or reprice billing. Source `coverage` and `finalized` metadata are preserved rather than used to derive a second resource-completeness result. Runtime stores no processed resource metrics.

Resource reads have an independent `resources` retry operation, with no default retry count/backoff policy. Retry re-reads the same scope and never creates/restarts an Agent or resubmits work. `AgentResourceCollection.status` is only `pending | collected | failed`: collected means the original snapshot was saved, not that the source is complete. Exhausted/unretryable reads are persisted as failures and do not change the Agent/output result or replace its original error. `getSampling()` and EvaluationRecord queries expose these durable facts even from a new Runtime instance; Metrics consumes Runtime/Dataset public queries rather than SP or private Store tables. Artifacts and complete trajectories still use references; resource snapshots store source resource events, not an additional Workspace or Session copy. Subject artifacts and the complete trajectory are required: after a terminal Submission, execution stays nonterminal until both references and the final execution status are saved together. `execution.evidencePending` marks evidence finalization for recovery without submitting or restarting the Agent; the original Agent failure is preserved.

Agent terminal facts are captured immediately on observation, before resource collection or persistence. The terminal Attempt is saved before resource collection so a later resource write failure cannot erase the already-observed Agent result. The same terminal status and completion time are retained through all subsequent errors. A completed Attempt never becomes failed because Runtime finalization failed; the owning execution/evaluation stage's `lastError` records that separate failure. Record writes use an independent `persistence` retry operation: the expected immutable record is captured once, a failed write is reconciled against the latest stored facts, and any retry saves the same record without collecting resources/output again or creating, submitting or restarting an Agent. Reconciliation compares JSON facts without depending on object property order, while retaining array ordering, duplicates and null values. The same stage RetryController is shared by lifecycle and persistence rather than allocating a fresh allowance for each write. No default persistence retry count or backoff is prescribed. This applies to resource records, terminal Attempt facts, output saves and cancellation/error finalization, not Run admission.

Pipeline cancellation writes for failed executions run independently of the successful Samplings' evaluation scheduler. Each cancellation reconciles/retries only its own EvaluationRecord. If cancellation cannot be saved, its finalization error is recorded on that EvaluationRecord, never on another Sampling, and already-confirmed cancellation is not downgraded. Successful Samplings do not wait for unrelated cancellation retries. If even the local error record cannot be persisted, `EvalRunResumerDependencies.onError` receives a scoped Error (console error reporting is the default); there is no silent discard or global failure rewrite caused by an unrelated cancellation. No new Run state, version, operation registry or orchestration entity is added.

Every Runtime Sampling/Evaluation update carries the previous persisted facts as its expected value. A Store atomically replaces a record only while those facts still match. A changed record is read and reconciled, never overwritten by an old full-record snapshot. This conditional write adds no persisted version. If write and read-back both fail until the persistence budget is exhausted, Runtime treats the commit outcome as unknown and leaves the stage recoverable; lifecycle error handling cannot write a failure status from stale memory. A collected resource snapshot remains intact when a later refresh fails, with the refresh error reported separately. Finalized snapshots are not refreshed.

### `eval-metrics`

Owns three internal submodules: `evaluators` interprets EvaluationRecord outputs, `aggregation` processes resources and groups statistics, and `reporting` serves Project/Dataset/Sample/Sampling views. There is no independent evaluator execution or attribution workflow. It reads original Dataset/Runtime facts, including failed/cancelled/restarted work, without querying SP or repricing bills. Resource interpretation, source-identity deduplication, parent/child overlap handling, model/Token normalization, costs, tool/request/Turn counts, durations, success rates and all higher-level summaries belong here, not in Runtime.

`MetricsSource.read(query)` is the application's read-only, consistent Dataset/Runtime projection port, not another Store. It returns the Project, Dataset snapshots, runtime Samples, Sampling snapshots, EvaluationRecords and Run snapshots required by the query. Applications can reuse public queries or provide a transactional read projection; the package does not access private Store tables or implement PostgreSQL/DO/R2 adapters. Source results are detached before processing. Every view requires an explicit Project scope; the application source uses that Project's owner to restrict Dataset, Data and Sample reads. Optional Run selection restricts both Sampling and Evaluation identities to those Runs. Without Run selection, the source returns every EvaluationRecord in the current Project state; admission deletes replaced evaluations. Shared Data can occur in several Dataset views of the same user; Project statistics aggregate distinct Samplings directly, not Dataset subtotals.

Scores keep their supplied scale. A failed Agent, a Runtime finalization error and an unreported score remain different facts. Missing or invalid scores are not zero; score distributions are grouped by evaluator identity, not averaged across different judges. Stage success rates use terminal records as the denominator; durations describe Agent attempt spans, not a batch's parallel wall-clock time.

Resource totals carry `complete | partial | unavailable` coverage and nullable values. Complete empty source streams can prove zero; absent, pending, failed, unfinalized or unsupported data cannot. Usage identity is owner plus eventId, telemetry identity is session plus eventId, operation identity is session plus operationId, and model settlement identity is accountId plus eventId. Missing source identities or contradictory duplicates are diagnosed rather than silently counted. Action charges use their execution identity. Provider USD, model debits, rated/shortfall/platform-owned units and actual Action charges stay separate; the package does not derive charges from prices or tool estimates. A Subagent summary suppresses child detail only for each individual Token or Provider USD metric that contains a valid value; missing summary metrics keep valid child detail and report the resulting coverage. Actual distinct billing settlements remain authoritative charges. SP input/output/cache buckets are disjoint, while reasoning is an output subset and is not added to total tokens. Model requests and Turns are counted from distinct telemetry operations, not usage rows or model-request/Turn equivalence. Per-tool outcomes and durations come from paired start/terminal events. Parsing does not mutate any raw source records.

The recognized billing facts are SP's model settlement receipt with its authoritative `accountId` and public Action log entries using `executionId` and `chargedCredits`. An in-progress Action is not a settlement, even if its provisional charged field is zero. Unsupported statuses and private database row layouts are not reinterpreted as final charges. The resource carrier still preserves those original records for diagnostics.

Ambiguous subagent summaries and cyclic parent relationships are diagnosed and cannot suppress trustworthy child details. Contradictory terminal outcomes or tool names remain unknown instead of picking a winner. Project counts describe Data associated with observed Samplings; Dataset counts describe that Dataset's complete current catalog, including Data without runs.

The implemented files are `evaluators/model.ts`, `evaluators/index.ts`, `aggregation/model.ts`, `aggregation/resources.ts`, `aggregation/resource-facts.ts`, `aggregation/resource-usage.ts`, `aggregation/resource-billing.ts`, `aggregation/resource-telemetry.ts`, `aggregation/statistics.ts`, `aggregation/index.ts`, `reporting/model.ts` and `reporting/index.ts`, plus focused tests and the root entry `index.ts`, which exports `createMetrics`, the error classes (`MetricsEntityNotFoundError` for an unknown Project, Run, Dataset, Sample or Sampling) and the model types. Experiment comparison, metric persistence/caches and application UIs are not introduced in this phase.

### `apps/eval-api`

Independent-evaluation Run views are read through one owner- and Project-scoped, consistent PostgreSQL snapshot. The adapter fetches the Run and its Sampling/Evaluation facts in sets, then uses the public Runtime projection for status; the HTTP composition does not issue one query per child record.

Internal control-plane composition boundary. Its authenticated HTTP API is specified in [Eval HTTP control plane](eval-http-api.md): every request is scoped to one fixed Eval SP service account, whose long-lived session is verified with Eval SP at startup, and composes only that account's Dataset, Catalog, Config, Runtime and Metrics services. The public Run admission endpoints persist work for the separate Worker; they do not run Agents in the HTTP process. Its PostgreSQL adapters implement the public `DatasetStore` and `RuntimeStore` ports, and one read-only `MetricsSource` over a consistent Dataset/Runtime snapshot. The adapters share a caller-injected Drizzle/`pg` connection; the application does not import SP private database code or read Durable Object storage. Database migrations, not process memory, enforce same-owner Dataset/Data/Sample, Sampling/Project and Run/Sampling relationships, atomic Dataset imports and Project-scoped Run idempotency uniqueness. The owner-scoped Catalog provides a paged query for successful Project Samplings and an all-matching-ID query using the same predicate and stable order. The HTTP control plane can submit that fixed ID list to Runtime; a retry must not resolve a changing success set. The selection and submission contract is specified in [Independent evaluation entry](eval-independent-evaluation-entry.md). Runtime Sample input is stored once in the Catalog as a reference to its owner's Data; Sampling/Evaluation keep their original raw facts, including all attempts and resources. A Run stores immutable scope and effective config, while its current progress is projected using the Runtime's own projection functions, never saved as a second status. Replacement of prior Project state and the retired-key ledger follow [Run admission](architecture.md#run-准入与独立评估).

The application also owns the Node Run Worker, not a fifth package. Run admission and stop requests enqueue a pg-boss job in the same PostgreSQL transaction as the Run facts; Worker instances consume it and invoke Runtime `resume(runId)` with the saved configuration. `createEvalRunResumer` exposes only recovery and requires Sample and output-schema lookup, Store and Harness; admission Catalog and ConfigResolver stay in the API control plane. The same admission transaction records the first Run's operation and config ID on Project, leaving an unlaunched Project unchanged if admission fails. A new empty Project cannot begin with evaluation-only because successful Samplings must already exist in that Project; later independent evaluation does not alter the first selection. pg-boss owns the job table; no duplicate Run status is added. Several Worker instances may run at once; scheduling, recovery and its remaining risks are recorded in [Run scheduling and stop](architecture.md#run-调度与停止). The Eval-side SP Harness calls the public routes implemented on the independent SP branch; real cross-deployment verification remains.

Projects have an ownerUserId; the target Project model also binds the deployed SP Git branch. Dataset, Data and Sample are owned by one Eval SP user; Data is reusable across that user's datasets and Projects, never across owners. The application Store must scope every user-facing read, write, import and association to the authenticated user and enforce same-owner references in PostgreSQL. Sampling and Run rows carry the same owner as their Project, Sample and membership through composite foreign keys. Every Run has one required `idempotencyKey` and request fingerprint, unique within its Project; another Project may use the same key. The Worker Store remains global and does not interpret these keys without a Run owner. The Catalog stores Projects and Samples and delegates Agent listing to an injected provider for the independent Eval SP API. The user-facing RuntimeStore and `MetricsSource` require the fixed service account identity that Eval SP verifies at startup; they apply that identity in SQL for Project, Run, Sampling and Evaluation reads and writes. A separate Worker RuntimeStore can resume any user's Run and must never be exposed through HTTP. `MetricsSource` limits reads to the requested Project and optionally selected Runs, limits both Sampling and Evaluation records, includes the current independent evaluation when no Run is selected, and reads under a single repeatable-read, read-only transaction. Dataset membership is current owner-scoped catalog state; no Dataset/Sample/Run version is introduced. Eval SP owns the service account and its `user-agent` library; Eval stores only Agent Config references and its own immutable Execution/Evaluation configuration records. Each Run saves its effective config snapshot; `pipeline` only sequences the two independently startable operations. The concrete public SP HTTP/WebSocket client belongs to this application composition layer, not a fifth shared package.

`ConfigStore` remains Runtime's read-only port. The Eval API application owns configuration creation, editing and listing through an owner-scoped PostgreSQL adapter: an ExecutionConfig references an owned Dataset and may select Samples currently in that Dataset; an EvaluationConfig stores an Eval SP Agent Config reference for the same owner; a PipelineConfig references that owner's ExecutionConfig and EvaluationConfig. PostgreSQL foreign keys enforce the Dataset and Pipeline references, so a Dataset referenced by an ExecutionConfig cannot be deleted. The adapter checks Dataset membership under a lock in the save transaction and uses the authenticated Eval SP client to verify each Agent Config's real owner before saving. Configuration IDs come from the server, while edits use the path ID. Runtime admission uses a separate owner-scoped, read-only ConfigStore projection, so its cached Runtime instance does not retain an individual login token. Editing a saved config changes future admissions only; an admitted Run keeps its effective config snapshot. The adapter never stores an Agent Config body or uses the global Worker Store for user requests.

### `apps/eval-web`

Future internal UI entry point. It will select Project, Dataset, Sample, Subject Agent, Judge Agent, execution concurrency and evaluation concurrency, then render Run, artifacts, metrics and Evaluation Agent evidence.

### `apps/eval-cli`

Future CLI entry point. It will use the same config and API semantics as Web; it is not the source of truth for Cloudflare Agent trajectories.

## SP alignment

The runtime Harness must consume the same public concepts as `sp-platform`:

- Agent Config reference in the independent Eval SP `user-agent` library: `ownerUserId`, `userAgentId`;
- ordinary Inbox/Chat ensure in the independent Eval SP deployment, with an optional immutable `evaluationWorkspace` binding for Evaluators; these Chats do not appear in dev/production Inbox;
- `dispatchMessage(message, "enqueue" | "steer")`;
- `SubmissionReceipt` and `getSubmission()`;
- `TrajectoryPage` pagination with SP's maximum page size;
- Workspace tree, manifests and content boundaries.

Runtime now records a preassigned Chat ID on Sampling/EvaluationRecord and the actual per-attempt Submission ID on each Attempt. The concrete SP Harness returns the real Submission ID from SP receipts and inspects uncertain operations by Chat and key; Runtime persists the result on each Attempt.

The Eval UI lists Chats through Run/Sampling/Evaluation rather than an Inbox management screen. Viewing Chat, Workspace and Trajectory is read-only for interactive users; only the controlled Run Worker submits work. The independent SP branch implements unattended decisions, Evaluator Workspace binding, Subject trajectory materialization and operation-scoped resource reads. Eval Web's read-only Chat/Workspace/Trajectory views and their interactive access policy still require integration and cross-deployment verification.

The Chat ID is assigned before provisioning and reused after an uncertain creation response. `ensureAgent` retries retain the same creation facts and Chat ID; a separately requested re-evaluation receives a new Evaluator Chat and EvaluationRecord identity. Chat creation identity is distinct from the idempotency key used to submit or restart work inside that Chat.

The eval project must not import SP private source files, use Web projections as facts, or read Durable Object SQLite directly.
