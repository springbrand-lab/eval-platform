# Eval SP Harness service contract

This is the service contract consumed by `apps/eval-api`. The independently deployed SP Agent Worker exposes the user-scoped routes below. Eval must not call SP Durable Object storage or private source modules. SP's `@springbrand/eval-harness` package is the single definition of the route paths, the service header, request schemas, Submission receipts, canonical Session validation and Material path and file-count rules; `apps/eval-api/src/sp/` imports them and validates every request against SP's schema before sending it.

The Eval Run Worker calls the independently deployed Eval SP origin with `X-Eval-Service-Token`. SP authenticates the service and checks the requested user, Agent Config, Chat, and Workspace ownership. HTTP responses below are bare JSON. A `409` on Chat ensure means immutable creation facts conflict; an unknown operation lookup returns JSON `null` with `200`, while an unknown Chat is an error. Retries use the original Chat ID and operation key. Both Eval SP clients (this service client and the API's session/Agent Config client) use `@springbrand/http/client`: redirects are rejected, response size is bounded, and network errors, timeouts, `408`, `429` and `≥500` are retryable. In addition, a Harness `GET` answered `409` with code `EVIDENCE_NOT_READY` is retryable (see [Readiness](#readiness-and-large-transfers)); every other `409`, and any `409` on a `PUT`, is not.

| Operation | Target route | Request / response |
| --- | --- | --- |
| Ensure ordinary Inbox Chat | `PUT /internal/v1/eval-harness/users/{userId}/chats/{chatId}` | `EnsureAgentInput` / `AgentHandle`; SP validates owner, Project, Sampling, role, `sp` framework, Agent Config and `evaluationId`, which is required for, and only for, Evaluators. An Evaluator is an ordinary Chat with its own Space; it is not bound to the Subject. |
| Initialize Chat | `POST /internal/v1/eval-harness/users/{userId}/chats/{chatId}/initialization` | `{idempotencyKey,data,initialSession?,initialMaterials?:[{bundleId,materialId,files}],evaluationOutputSchema?:{content}}` / `MaterializedDataBinding` `{manifestHash,target,materials:[{bundleId,materialId,rootPath}],evaluationOutputSchemaPath?}`. See [Initialization](#initialization). |
| Submit or restart | `POST /internal/v1/eval-harness/users/{userId}/chats/{chatId}/submissions` | `{idempotencyKey,prompt,runtime?,unattended:true}` / `AgentSubmission` with the real Submission ID. A new key in one Chat creates a new Submission; the same key recovers the original. SP handles approvals and `ask_user` without an observer connection. |
| Inspect operation | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/submissions/by-key/{key}` | `AgentSubmission` or `null` for an absent key; a missing Chat returns `404`. No write or replacement Submission. |
| Inspect known Submission | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/submissions/{submissionId}` | The same `AgentSubmission` projection as by-key, or `404`. Eval uses it for every status read after it has a real Submission ID (WebSocket calibration). There is no operation-key fallback: `404` means the Submission or its Chat no longer exists and ends observation with `AgentHandleNotFoundError`. |
| Stop Eval Chat | `POST /internal/v1/eval-harness/users/{userId}/chats/{chatId}/submissions/stop` | `{ok:boolean}`; SP durably blocks future initialization and Submissions in this Eval-bound Chat, waits for submissions already being accepted, then interrupts every unfinished Submission before returning. A missing Chat is `404`; repeated stop after terminal work returns `{ok:false}`. |
| Observe terminal | `WS /internal/v1/eval-harness/users/{userId}/chats/{chatId}/submissions/{submissionId}/events` | Authenticate the upgrade with `X-Eval-Service-Token`. On connect SP sends a persisted status snapshot, then `{"type":"submission.status","submission":AgentSubmission}` updates for this Submission. The endpoint answers protocol Ping with Pong. Eval detects a silent connection with Ping/Pong, performs one HTTP status read after each disconnection (by Submission ID, see above), and reopens the same Submission URL up to three connections. A transient read error does not end observation: the status is unknown, not failed. A terminal read ends observation; a different Submission ID is a non-retryable error. When the budget or the Submission deadline is spent, Eval raises a retryable error `Submission {id} status unconfirmed after N connections: {socket failure}; last status read: {status \| HTTP n \| error}`, so Runtime re-observes the same Submission instead of treating the Agent as failed. Healthy progress uses the socket, not polling. |
| Collect output | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/output?role=...&samplingId=...&evaluationId=...` | `ExecutionOutput` or `EvaluationAgentOutput`. SP returns the complete artifact list and complete trajectory reference, including failed runs. An `EvaluationAgentOutput` carries the Evaluator's result file `/output/result.json` from its own Space as `structuredOutput: {path, content, contentHash?}` with the original UTF-8 text, or omits it when no file exists (SP-side support still required, see [SP requirements](sp-eval-api-requirements.md)). Results submitted through Eval's own MCP tool take precedence; see [Evaluation result submission](eval-evaluation-result-submission.md). |
| Collect raw resources | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/resources/by-key/{key}?submissionId=...` | `AgentResourceSnapshot` with source events, `coverage` and `finalized` unchanged, plus the required `readiness: {receiptTerminal, stateUnreadable, pendingTelemetryEvents, pendingRuntimeEvents, actionCharges: {complete, unsettledExecutions, missingExecutionIds}}` explaining `finalized` (all counts non-negative integers). Eval rejects a snapshot without valid `readiness` and stores it unchanged with the snapshot; only snapshots persisted before this contract lack it. The response carries the complete raw telemetry, can exceed 100 MB, and is streamed by SP. SP resolves a missing Submission ID by Chat and key; it never substitutes Chat ID. |
| Inspect resource readiness | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/resources/by-key/{key}/readiness?submissionId=...` | `AgentResourceReadinessReport` `{scope:{chatId,idempotencyKey,submissionId}, observedAt, finalized, readiness}` without any events: the same `finalized` and `readiness` the snapshot route would return now. Same scope and optional `submissionId` as the snapshot route; a small body under the 60 s control timeout. See [Waiting for resources](#waiting-for-resources). |
| List evidence artifacts | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/evidence/artifacts?submissionId=...` | `{artifacts:[{path,size,mediaType}]}`: files the Agent produced in its own Space, excluding `/reference`, `/initial-materials`, `/userspace`, `/evidence` and uploads. |
| Read evidence file | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/evidence/files?path=...&submissionId=...` | Raw, streamed bytes of one listed file; `413` when it exceeds the package's `EVAL_EVIDENCE_FILE_MAX_BYTES` (`95_000_000` in `@springbrand/eval-harness@0.1.0-alpha.4`, which Eval pins; the limit is in effect). Eval omits larger artifacts as `too-large` before reading them. |
| Read evidence trajectory | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/evidence/trajectory?afterSeq=...&limit=...&submissionId=...` | `{events:[{ingestSeq,event}], nextAfterSeq}`, oldest first from `trajectory_events`, `limit` ≤ 200, `nextAfterSeq` is `null` on the last page. Eval writes each `{ingestSeq,event}` entry unchanged as one `sp-trajectory/v1` JSONL line, and a resumed export starts at the `ingestSeq` of the last stored part. All three evidence reads require `submissionId`: the Subject Attempt's for an export, and the Evaluator Attempt's for `readFinalReply`; Eval always sends it. All three export routes return `409 EVIDENCE_NOT_READY` with `Retry-After` until the last Submission is terminal and its telemetry is delivered; Eval treats that code as retryable on every Harness `GET`, including Collect output. The same route serves an Evaluator Chat, from which `readFinalReply` takes the assistant text of the last `turn.finished` event. |
| Import evidence file | `PUT /internal/v1/eval-harness/users/{userId}/chats/{chatId}/evidence/files?path=/relative` | Raw body with `Content-Type` and `X-Eval-Content-Sha256: <hex>` / `{path:"/evidence/...",size,sha256}`. Evaluator Chats only. Eval streams each stored blob (chunked, half-duplex) rather than buffering it, verifying size and SHA-256 against the manifest while it streams; a mismatch aborts the upload as a non-retryable error. An identical repeat is a no-op; different content is `409`, a path escaping `/evidence` is `422`, and a write after stop is `409`; none of these is retried. Eval writes the manifest last. The Run Worker gives Runtime `spEvidenceLimits(DEFAULT_EVIDENCE_LIMITS)`, so artifacts and trajectory parts are exported within `EVAL_EVIDENCE_FILE_MAX_BYTES`. Before any write Eval still checks every manifest file against it; a larger file (only possible in a bundle stored under larger limits) fails the import explicitly and permanently. |

The Run Worker process consumes pg-boss Run jobs, reads the persisted Run, its Project plan and ProjectSample snapshots, and composes Runtime with this Harness; on shutdown it stops fetching jobs and waits for active Runs. It uses this service contract; browser session tokens are never stored for background execution. This release's concrete Harness rejects `codex` and `cc` ("SP Harness cannot run {framework} Agents") rather than falling back to SP. Initialization does not send `runtime`; SP receives it when ensuring a Chat or submitting a prompt, while Eval uses it to bound terminal observation. Submission observation over WebSocket lives in `sp/submission-observer.ts`.

`start:worker` reads initial resources from `EVAL_BUNDLE_DIR`, the absolute directory shared with the API. For user `{ownerUserId}`, Bundle `{bundleId}`, Material `{materialId}` and Session `{sessionId}`, the files are `{root}/{ownerUserId}/{bundleId}/materials/{materialId}.json` in a Material Bundle and `{root}/{ownerUserId}/{bundleId}/sessions/{sessionId}.json` in a Session Bundle; every segment is a lowercase platform UUID, so no ID can act as a path segment, and the user directory isolates owners. A Material file is `{ "files": [{ "path": "/brief.txt", "mediaType": "text/plain", "contentBase64": "..." }] }` and must satisfy SP's Material file rules. A Session file is `{ "format": "json" | "jsonl", "content": "..." }` and is checked with SP's `readEvalCanonicalContext`, which owns the canonical entry format, duplicate-key handling and size limits. Resolved paths must stay inside the owner directory. Content under one ID is immutable; changed content conflicts with SP initialization facts.

A ProjectSample without materials needs no material file. Material and Session files referenced by a Project remain readable by ID after their catalog entries are soft-deleted. Any referenced material missing from its Bundle fails initialization explicitly. A referenced initial Context must resolve to its uploaded content; a missing file fails initialization rather than silently starting an empty Context.

## Readiness and large transfers

- **Not ready is not failed.** `409` with error code `EVIDENCE_NOT_READY` on a Harness `GET` (evidence artifacts, files, trajectory pages, output) means the Submission or its telemetry has not settled. Eval raises a retryable `SpHarnessError` with `status: 409` and SP's `Retry-After` as `retryAfterMs` (capped at 30 s by the HTTP client). Runtime's own bounded backoff schedules the repeat; the hint is carried for diagnostics. Any other `409` (for example `REQUEST_CONFLICT`) stays non-retryable, as does every `PUT 409`.
- **Size ceilings.** A JSON response is decoded into one string before `JSON.parse`, so the ceiling is V8's maximum string length (`buffer.constants.MAX_STRING_LENGTH`, 536,870,888 bytes ≈ 512 MiB; each UTF-8 byte yields at most one UTF-16 unit, so any body within it decodes). A larger body fails with the non-retryable `Eval SP resource snapshot exceeded the N-byte response limit` (or the matching label for other reads) instead of being truncated or retried. Evidence file bytes are not JSON and are bounded only by SP's per-file limit above.
- **Persistence ceiling.** A collected snapshot is stored inside the Sampling/Evaluation `facts` JSONB value, whose PostgreSQL limit is about 255 MB. A snapshot between that and the response ceiling is read but cannot be persisted; storing raw telemetry outside `facts` is a follow-up.
- **Timeouts.** Control calls, including the readiness route, keep the 60 s request timeout and stop keeps 10 s. Resource snapshots, evidence artifact lists, trajectory pages and evidence file reads/writes use a separate 5-minute transfer timeout (`transferTimeoutMs`), which covers reading the whole streamed body.

## Waiting for resources

A snapshot is downloaded once, after SP reports it final, instead of re-reading 100+ MB until it is:

1. Every Harness call, the readiness route and the snapshot included, uses Runtime's fixed inner budget of ten retries for transient failures. Snapshot downloads count against it on the Attempt before each one, so a crashed download counts too; once it is spent Runtime gives the snapshot up instead of downloading again. A process downloads one snapshot at a time.
2. When the Agent ends, Runtime polls the readiness route in the same pass after 5, 10, 20 and 40 s. As soon as `finalized` is true it downloads the full snapshot once.
3. If it is still not final, the stage keeps `resourcesPending` with a `deadline` ten minutes after the Agent ended; later Worker passes check readiness every 60 s until the deadline. A Run waiting for nothing else is woken by a delayed job at its earliest `nextAttemptAt`, so idle waits spend no retry. At the deadline Runtime downloads the current snapshot once and stores it as it is (`finalized: false`, with SP's `readiness`).
4. A manual `resources` recollection starts the same wait with a new ten-minute deadline.

Eval does not trigger delivery of SP's telemetry/runtime outboxes; it only waits for it. Draining them on demand needs a guarded flush API in `@springbrand/agent-runtime` (follow-up).

## Diagnostics

The Harness accepts an optional `log(event)` sink (the Runtime's `RuntimeLog` type), wired by the Run Worker to the same pino sink as the Runtime log (`error` for `retry_exhausted`; `warn` for an event with `error`, `ws_reconnect` and `operation_retry`; otherwise `info`). Events carry identifiers (role, Chat, Sampling, Evaluation, operation key, Submission), HTTP status, declared byte counts and durations, never prompts, payloads, events, file bytes or the service token; a failure's `error` is `errorDiagnostics` output, plus SP's `X-Request-ID` as `requestId` and Cloudflare's `cf-ray` as `cfRay` when the response carried them (`cfRay` only on evidence byte requests, whose raw headers the Harness reads). Events: `ws_open`, `ws_close` (`code`, `reason`), `ws_inspect` (`outcome`: status, `HTTP n` or `error (...)`), `ws_reconnect`, `submission_terminal` (`source`: `socket` or `inspect`), `resources_read` (`status`, `finalized`, `coverage`, event counts and SP's `readiness` unchanged), `resources_readiness` (`status`, `finalized`, `readiness`), `evidence_trajectory_page` (failed pages, and the final page with `from`, `pages`, `events`), `evidence_file` (failures only: `direction`, `path`, `status`) and `evidence_import` (`evidenceId`, `filesStored`/`filesTotal` including the manifest, `bytes`, `durationMs`, `outcome`). Successful file transfers are covered by the Runtime's `evidence_export` and this `evidence_import` summary.

## Initialization

One initialization call carries everything a Chat receives before its first Submission; SP keeps a single initialization fact per Chat, so the call is never split.

- `initialMaterials` carries every material of the role in Data order: the Subject's `initialMaterials`, or the Evaluator's `evalInitialMaterials`, which Runtime passes as the Evaluator's own `data.initialMaterials`. Entry *i* has the same `{bundleId, materialId}` as entry *i* of `data.initialMaterials` and carries that Material's resolved `files`. The field is omitted when the role has no materials.
- SP writes each Material below its own root `/initial-materials/{bundleId}/{materialId}`,, so different Materials never share a path.
- `initialSession` is the single optional Session reference of the Subject; its resolved context is canonical JSON or JSONL. Messages use Pi's native format: assistant content is a block array with model, usage, timestamp and stop reason; user messages also carry a timestamp. A role/content-only transcript is invalid. SP's shared reader validates this format, and initialization rejects invalid history before reserving input facts or importing it. An Evaluator never sends one.
- `evaluationOutputSchema: {content}` is sent for every Evaluator and never for a Subject. `content` is the evaluation plan's JSON Schema text; SP writes it to the fixed path `/evaluation-output.schema.json`, independent of the Materials.
- Limits are SP's rules applied to the whole initialization: at most `EVAL_MATERIAL_MAX_FILES` (500) files per Material, `EVAL_INITIAL_FILE_MAX_BYTES` (5 MB) per file and `EVAL_INITIALIZATION_MAX_BYTES` (20 MB) in total across all Materials and the output Schema file. Eval rejects a Data field whose bound Materials exceed the total when it is written (see [Dataset upload](eval-dataset-upload.md)).
- The result `MaterializedDataBinding` is `{manifestHash, target, materials, evaluationOutputSchemaPath?}`: `materials` lists `{bundleId, materialId, rootPath}` in request order, and `evaluationOutputSchemaPath` is present only for an Evaluator.

## Eval control-plane resource APIs

Uploads and Data associations are separate authenticated Eval API operations; their routes and bodies are specified in [Dataset upload](eval-dataset-upload.md). The owner comes from the verified Eval SP session, never from a client field. Uploads write only to the authenticated user's Bundle directory, each under a newly generated resource ID; an existing resource file is never overwritten. Binding updates only the chosen Data references atomically and never uploads bytes; resource upload never edits Data. Pipeline and evaluation Run admission requires a Project evaluation plan; the Worker resolves the plan's output-schema ID to the saved, immutable Schema content.
