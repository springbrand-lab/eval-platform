# Eval SP Harness service contract

This is the service contract consumed by `apps/eval-api`. The independently deployed SP Agent Worker exposes the user-scoped routes below. Eval must not call SP Durable Object storage or private source modules. SP's `@springbrand/eval-harness` package is the single definition of the route paths, the service header, request schemas, Submission receipts, canonical Session validation and Material path and file-count rules; `apps/eval-api/src/sp/` imports them and validates every request against SP's schema before sending it.

The Eval Run Worker calls the independently deployed Eval SP origin with `X-Eval-Service-Token`. SP authenticates the service and checks the requested user, Agent Config, Chat, and Workspace ownership. HTTP responses below are bare JSON. A `409` on Chat ensure means immutable creation facts conflict; an unknown operation lookup returns JSON `null` with `200`, while an unknown Chat is an error. Retries use the original Chat ID and operation key. Both Eval SP clients (this service client and the API's session/Agent Config client) use `@springbrand/http/client`: redirects are rejected, response size is bounded, and network errors, timeouts, `408`, `429` and `≥500` are retryable.

| Operation | Target route | Request / response |
| --- | --- | --- |
| Ensure ordinary Inbox Chat | `PUT /internal/v1/eval-harness/users/{userId}/chats/{chatId}` | `EnsureAgentInput` / `AgentHandle`; SP validates owner, Project, Sampling, role, `sp` framework, Agent Config and `evaluationId`, which is required for, and only for, Evaluators. An Evaluator is an ordinary Chat with its own Space; it is not bound to the Subject. |
| Initialize Chat | `POST /internal/v1/eval-harness/users/{userId}/chats/{chatId}/initialization` | `{idempotencyKey,data,initialSession?,initialMaterials?}` / `MaterializedDataBinding`; the role-specific Data material reference resolves to file bytes before this call. Every Evaluator also receives the evaluation plan's JSON Schema as `evaluation-output.schema.json` below the returned `MaterializedDataBinding.rootPath` in its own Space. Session context is optional canonical JSON or JSONL. |
| Submit or restart | `POST /internal/v1/eval-harness/users/{userId}/chats/{chatId}/submissions` | `{idempotencyKey,prompt,runtime?,unattended:true}` / `AgentSubmission` with the real Submission ID. A new key in one Chat creates a new Submission; the same key recovers the original. SP handles approvals and `ask_user` without an observer connection. |
| Inspect operation | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/submissions/by-key/{key}` | `AgentSubmission` or `null` for an absent key; a missing Chat returns `404`. No write or replacement Submission. |
| Stop Eval Chat | `POST /internal/v1/eval-harness/users/{userId}/chats/{chatId}/submissions/stop` | `{ok:boolean}`; SP durably blocks future initialization and Submissions in this Eval-bound Chat, waits for submissions already being accepted, then interrupts every unfinished Submission before returning. A missing Chat is `404`; repeated stop after terminal work returns `{ok:false}`. |
| Observe terminal | `WS /internal/v1/eval-harness/users/{userId}/chats/{chatId}/submissions/{submissionId}/events` | Authenticate the upgrade with `X-Eval-Service-Token`. On connect SP sends a persisted status snapshot, then `{"type":"submission.status","submission":AgentSubmission}` updates for this Submission. The endpoint answers protocol Ping with Pong. Eval detects a silent connection with Ping/Pong, performs one HTTP inspection after disconnection, and reopens the socket a finite number of times; a transient inspection error does not suppress the next socket attempt. Healthy progress uses the socket, not polling. |
| Collect output | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/output?role=...&samplingId=...&evaluationId=...` | `ExecutionOutput` or `EvaluationAgentOutput`. SP returns the complete artifact list and complete trajectory reference, including failed runs. An `EvaluationAgentOutput` carries the Evaluator's result file `/output/result.json` from its own Space as `structuredOutput: {path, content, contentHash?}` with the original UTF-8 text, or omits it when no file exists (SP-side support still required, see [SP requirements](sp-eval-api-requirements.md)). |
| Collect raw resources | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/resources/by-key/{key}?submissionId=...` | `AgentResourceSnapshot` with source events, `coverage` and `finalized` unchanged. SP resolves a missing Submission ID by Chat and key; it never substitutes Chat ID. |
| List evidence artifacts | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/evidence/artifacts` | `{artifacts:[{path,size,mediaType}]}`: files the Agent produced in its own Space, excluding `/reference`, `/initial-materials`, `/userspace`, `/evidence` and uploads. |
| Read evidence file | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/evidence/files?path=...` | Raw bytes of one listed file; `413` when it exceeds 25 MB (one file per Durable Object RPC). |
| Read evidence trajectory | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/evidence/trajectory?afterSeq=...&limit=...` | `{events:[{ingestSeq,event}], nextAfterSeq}`, oldest first from `trajectory_events`, `limit` ≤ 200, `nextAfterSeq` is `null` on the last page. Eval maps each event to `eval-trajectory/v1` and keeps the original in `raw`. All three export routes return `409` until the last Submission is terminal and its telemetry is delivered. |
| Import evidence file | `PUT /internal/v1/eval-harness/users/{userId}/chats/{chatId}/evidence/files?path=/relative` | Raw body with `Content-Type` and `X-Eval-Content-Sha256: <hex>` / `{path:"/evidence/...",size,sha256}`. Evaluator Chats only. An identical repeat is a no-op; different content is `409`, a path escaping `/evidence` is `422`, and a write after stop is `409`. Eval writes the manifest last. |

The Run Worker process consumes pg-boss Run jobs, reads the persisted Run, its Project plan and ProjectSample snapshots, and composes Runtime with this Harness; on shutdown it stops fetching jobs and waits for active Runs. It uses this service contract; browser session tokens are never stored for background execution. This release's concrete Harness rejects `codex` and `cc` ("SP Harness cannot run {framework} Agents") rather than falling back to SP. Initialization does not send `runtime`; SP receives it when ensuring a Chat or submitting a prompt, while Eval uses it to bound terminal observation. Submission observation over WebSocket lives in `sp/submission-observer.ts`.

`start:worker` reads initial resources from `EVAL_BUNDLE_DIR`, the absolute directory shared with the API. For user `{ownerUserId}`, Bundle `{bundleId}`, Material `{materialId}` and Session `{sessionId}`, the files are `{root}/{ownerUserId}/{bundleId}/materials/{materialId}.json` and `{root}/{ownerUserId}/{bundleId}/sessions/{sessionId}.json`; every segment is a lowercase platform UUID, so no ID can act as a path segment, and the user directory isolates owners. A Material file is `{ "files": [{ "path": "/brief.txt", "mediaType": "text/plain", "contentBase64": "..." }] }` and must satisfy SP's Material file rules. A Session file is `{ "format": "json" | "jsonl", "content": "..." }` and is checked with SP's `readEvalCanonicalContext`, which owns the canonical entry format, duplicate-key handling and size limits. Resolved paths must stay inside the owner directory. Content under one ID is immutable; changed content conflicts with SP initialization facts.

A ProjectSample without materials needs no material file. Material and Session files referenced by a Project remain readable by ID after their catalog entries are soft-deleted. A referenced material missing from the Bundle fails initialization explicitly. An initial Session may retain only its reference when its context file is absent.

## Eval control-plane resource APIs

Uploads and Data associations are separate authenticated Eval API operations; their routes and bodies are specified in [Dataset upload](eval-dataset-upload.md). The owner comes from the verified Eval SP session, never from a client field. Uploads write only to the authenticated user's Bundle directory; repeating identical content is safe, while changing content under the same ID conflicts. Binding updates only the chosen Data references atomically and never uploads bytes; resource upload never edits Data. Pipeline and evaluation Run admission requires a Project evaluation plan; the Worker resolves the plan's output-schema ID to the saved, immutable Schema content.
