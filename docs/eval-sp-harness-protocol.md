# Eval SP Harness service contract

This is the service contract consumed by `apps/eval-api`. The independently deployed SP Agent Worker exposes the user-scoped routes below. Eval must not call SP Durable Object storage or private source modules.

The Eval Run Worker calls the independently deployed Eval SP origin with `X-Eval-Service-Token`. SP authenticates the service and checks the requested user, Agent Config, Chat, and Workspace ownership. HTTP responses below are bare JSON. A `409` on Chat ensure means immutable creation facts conflict; an unknown operation lookup returns JSON `null` with `200`, while an unknown Chat is an error. Retries use the original Chat ID and operation key.

| Operation | Target route | Request / response |
| --- | --- | --- |
| Ensure ordinary Inbox Chat | `PUT /internal/v1/eval-harness/users/{userId}/chats/{chatId}` | `EnsureAgentInput` / `AgentHandle`; SP validates owner, Project, Sampling, role, `sp` framework, Agent Config and optional Evaluator Workspace binding. |
| Initialize Chat | `POST /internal/v1/eval-harness/users/{userId}/chats/{chatId}/initialization` | `{idempotencyKey,data,initialSession?,initialMaterials?}` / `MaterializedDataBinding`; each Sample’s material reference resolves to file bytes before this call. Session context is optional canonical JSON or JSONL. |
| Submit or restart | `POST /internal/v1/eval-harness/users/{userId}/chats/{chatId}/submissions` | `{idempotencyKey,prompt,runtime?,unattended:true}` / `AgentSubmission` with the real Submission ID. A new key in one Chat creates a new Submission; the same key recovers the original. SP handles approvals and `ask_user` without an observer connection. |
| Inspect operation | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/submissions/by-key/{key}` | `AgentSubmission` or `null`; no write or replacement Submission. |
| Stop Eval Chat | `POST /internal/v1/eval-harness/users/{userId}/chats/{chatId}/submissions/stop` | `{ok:boolean}`; SP persists abort intent and interrupts every unfinished Submission in this Eval-bound Chat before returning. A missing Chat is `404`; repeated stop after terminal work returns `{ok:false}`. |
| Observe terminal | `WS /internal/v1/eval-harness/users/{userId}/chats/{chatId}/submissions/{submissionId}/events` | Authenticate the upgrade with `X-Eval-Service-Token`. On connect SP sends a persisted status snapshot, then `{"type":"submission.status","submission":AgentSubmission}` updates for this Submission. The endpoint answers protocol Ping with Pong. Eval detects a silent connection with Ping/Pong, performs one HTTP inspection after disconnection, and reopens the socket a finite number of times; a transient inspection error does not suppress the next socket attempt. Healthy progress uses the socket, not polling. |
| Collect output | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/output?role=...&samplingId=...&evaluationId=...` | `ExecutionOutput` or `EvaluationAgentOutput`. SP returns the complete artifact list and complete trajectory reference, including failed runs. Subject files remain in its Workspace; Evaluator outputs stay under `/evaluations/{evaluationId}/`. |
| Collect raw resources | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/resources/by-key/{key}?submissionId=...` | `AgentResourceSnapshot` with source events, `coverage` and `finalized` unchanged. SP resolves a missing Submission ID by Chat and key; it never substitutes Chat ID. |
| Materialize Subject trajectory | `POST /internal/v1/eval-harness/workspaces/{userId}/{chatId}/trajectory` | `{idempotencyKey,samplingId,trajectory}` / `204`; SP reads the complete Subject trajectory and writes it once into the Subject SpaceDO. Evaluator preparation waits for confirmation. |

The Run Worker process reads persisted Run configuration and Sample references, composes the existing Runtime and PostgreSQL recovery worker, and exits only after active Runs drain. It uses this service contract; browser session tokens are never stored for background execution. This release's concrete Harness rejects `codex` and `cc` rather than falling back to SP. Initialization does not send `runtime`; SP receives it when ensuring a Chat or submitting a prompt, while Eval uses it to bound terminal observation.

The packaged `start:worker` reads external resources from `EVAL_BUNDLE_DIR`, an absolute directory mounted with the Worker. For user `{ownerUserId}`, Bundle `{bundleId}`, and material `{materialId}`, it reads `{root}/{ownerUserId}/{encodedBundleId}/materials/{encodedMaterialId}.json`. Each JSON file is `{ "files": [{ "path": "/brief.txt", "mediaType": "text/plain", "contentBase64": "..." }] }`. For Session `{sessionId}`, it optionally reads `{root}/{ownerUserId}/{encodedBundleId}/sessions/{encodedSessionId}.json`, containing `{ "format": "json" | "jsonl", "content": "..." }`. Canonical JSON content is `{ "entries": [{ "id": "...", "message": { "role": "user" | "assistant" | "toolResult", ... }, "createdAt": 0 }] }`; JSONL content contains one such entry per nonblank line. IDs are unique, timestamps are nonnegative safe integers, there are at most 10,000 entries, and a nonempty history starts with a user message. Each encoded ID is `encodeURIComponent(id)` with every `.` replaced by `%2E`, so IDs cannot act as path segments. The user directory isolates identical Bundle IDs owned by different accounts. Deployments mount the same immutable directory across Worker restarts; changed content conflicts with SP initialization facts.

`startSpEvalRunWorkerProcess` also accepts injected resolvers in its SP options. A Sample without materials needs no material file. A referenced material missing from the Bundle fails initialization explicitly. An initial Session may retain only its reference when its context file is absent.

## Eval control-plane resource APIs

Uploads and Data associations are separate authenticated operations. The control-plane HTTP server will mount these routes; `apps/eval-api` supplies the owner-scoped application operations. The owner comes from the verified Eval SP session, never from a client field.

| Operation | Route | Body / result |
| --- | --- | --- |
| Upload material resource | `PUT /api/bundles/{bundleId}/materials/{materialId}` | `{files:[{path,mediaType,contentBase64}]}` / `{bundleId,materialId}` |
| Upload Session context | `PUT /api/bundles/{bundleId}/sessions/{sessionId}` | `{format:"json"|"jsonl",content}` / `{bundleId,sessionId}` |
| Bind existing resources to one Data | `PATCH /api/data/{dataId}/initial-resources` | `{initialMaterials?,initialSession?}` / updated Data; omit a field to preserve it, `null` to clear it |

Uploads write only to the authenticated user's Bundle directory. Repeating identical content is safe; changing content under the same ID conflicts. The binding operation checks that supplied materials exist for that user; a Session reference may be bound without an uploaded context file. It then updates only the chosen Data references atomically. It never uploads bytes. Resource upload never edits Data.
