# Eval SP Harness service contract

This is the service contract consumed by `apps/eval-api`. The independently deployed SP Agent Worker exposes the user-scoped routes below. Eval must not call SP Durable Object storage or private source modules. SP's public `@springbrand/eval-harness` source owns the route paths, service header, request schemas, Submission receipts, canonical Session validation, Material paths and the Pi-native page wire. Its `0.1.0-alpha.7` package is **private/unpublished**; Eval still pins the published `0.1.0-alpha.5`, which does **not** export native/resource pages. Until SP actually publishes the new package, Eval checks only a structural HTTP consumer contract and reuses its existing `eval-contracts` native page schema; cross-deployment compatibility is unverified. See [cutover and parity checklist](pi-native-eval-cutover.md).

The Eval Run Worker calls the independently deployed Eval SP origin with `X-Eval-Service-Token`. SP authenticates the service and checks the requested user, Agent Config, Chat, and Workspace ownership. HTTP responses below are bare JSON. A `409` on Chat ensure means immutable creation facts conflict; an unknown operation lookup returns JSON `null` with `200`, while an unknown Chat is an error. Retries use the original Chat ID and operation key. Both Eval SP clients (this service client and the API's session/Agent Config client) use `@springbrand/http/client`: redirects are rejected, response size is bounded, and network errors, timeouts, `408`, `429` and `≥500` are retryable. Normally a Harness `GET` answered `409 EVIDENCE_NOT_READY` is retryable, except a post-wait opted-in partial page that SP cannot serve (see [Readiness](#readiness-and-large-transfers)); every other `409`, and any `409` on a `PUT`, is not.

| Operation | Target route | Request / response |
| --- | --- | --- |
| Ensure ordinary Inbox Chat | `PUT /internal/v1/eval-harness/users/{userId}/chats/{chatId}` | `EnsureAgentInput` / `AgentHandle`; SP validates owner, Project, Sampling, role, `sp` framework, Agent Config and `evaluationId`, which is required for, and only for, Evaluators. An Evaluator is an ordinary Chat with its own Space; it is not bound to the Subject. |
| Initialize Chat | `POST /internal/v1/eval-harness/users/{userId}/chats/{chatId}/initialization` | `{idempotencyKey,data,initialSession?,initialMaterials?:[{bundleId,materialId,files}],evaluationOutputSchema?:{content}}` / `MaterializedDataBinding` `{manifestHash,target,materials:[{bundleId,materialId,rootPath}],evaluationOutputSchemaPath?}`. See [Initialization](#initialization). |
| Submit or restart | `POST /internal/v1/eval-harness/users/{userId}/chats/{chatId}/submissions` | `{idempotencyKey,prompt,runtime?,unattended:true}` / `AgentSubmission` with the real Submission ID. A new key in one Chat creates a new Submission; the same key recovers the original. SP handles approvals and `ask_user` without an observer connection. |
| Inspect operation | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/submissions/by-key/{key}` | `AgentSubmission` or `null` for an absent key; a missing Chat returns `404`. No write or replacement Submission. |
| Inspect known Submission | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/submissions/{submissionId}` | The same `AgentSubmission` projection as by-key, or `404`. Eval uses it for every status read after it has a real Submission ID (WebSocket calibration). There is no operation-key fallback: `404` means the Submission or its Chat no longer exists and ends observation with `AgentHandleNotFoundError`. |
| Stop Eval Chat | `POST /internal/v1/eval-harness/users/{userId}/chats/{chatId}/submissions/stop` | `{ok:boolean}`; SP durably blocks future initialization and Submissions in this Eval-bound Chat, waits for submissions already being accepted, then interrupts every unfinished Submission before returning. A missing Chat is `404`; repeated stop after terminal work returns `{ok:false}`. |
| Observe terminal | `WS /internal/v1/eval-harness/users/{userId}/chats/{chatId}/submissions/{submissionId}/events` | Authenticate the upgrade with `X-Eval-Service-Token`. On connect SP sends a persisted status snapshot, then `{"type":"submission.status","submission":AgentSubmission}` updates for this Submission. The endpoint answers protocol Ping with Pong. Eval detects a silent connection with Ping/Pong, performs one HTTP status read after each disconnection (by Submission ID, see above), and reopens the same Submission URL up to three connections. A transient read error does not end observation: the status is unknown, not failed. A terminal read ends observation; a different Submission ID is a non-retryable error. When the budget or the Submission deadline is spent, Eval raises a retryable error `Submission {id} status unconfirmed after N connections: {socket failure}; last status read: {status \| HTTP n \| error}`, so Runtime re-observes the same Submission instead of treating the Agent as failed. Healthy progress uses the socket, not polling. |
| Collect output | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/output?role=...&samplingId=...&evaluationId=...` | `ExecutionOutput` or `EvaluationAgentOutput`. SP returns the complete artifact list and complete trajectory reference, including failed runs. An `EvaluationAgentOutput` carries the Evaluator's result file `/output/result.json` from its own Space as `structuredOutput: {path, content, contentHash?}` with the original UTF-8 text, or omits it when no file exists (SP-side support still required, see [SP requirements](sp-eval-api-requirements.md)). Results submitted through Eval's own MCP tool take precedence; see [Evaluation result submission](eval-evaluation-result-submission.md). |
| Legacy combined resources (**not used by new collection**) | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/resources/by-key/{key}?submissionId=...` | SP still serves a full resource JSON body for compatibility. Eval's new collector never calls it or silently falls back to it; a missing new page route fails collection. |
| Inspect resource readiness | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/resources/by-key/{key}/readiness?submissionId=...` | `AgentResourceReadinessReport` `{scope:{chatId,idempotencyKey,submissionId}, observedAt, finalized, readiness}` without any events: the same `finalized` and `readiness` the snapshot route would return now. Same scope and optional `submissionId` as the snapshot route; a small body under the 60 s control timeout. See [Waiting for resources](#waiting-for-resources). |
| Read resource header | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/resources/by-key/{key}/header?submissionId=...[&allowPartial=true]` | Small scope, readiness, `finalized`, coverage, `cursor:{throughSeq}` and separately settled `actionCharges:[{source:"action"\|"tool",executionId,status,chargedCredits}]`. No usage/billing or native arrays. Normal reads page only a finalized header. After Runtime's wait expires it opts into a nonfinalized known-facts snapshot explicitly; that partial cutoff is **not** pinned as the later finalized cutoff. A missing receipt ID is first resolved through operation-bound `/readiness`. Eval checks the header again for unchanged cutoff/charges/coverage/readiness. |
| Page scoped native records | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/resources/by-key/{key}/native-records?submissionId=...&afterSeq=...&limit=200&throughSeq=...[&allowPartial=true]` | The same `sp-pi-trajectory/v1` 200-row/4,000,000-byte page as evidence, but only the selected Submission and descendants with a verified same-Chat parent chain (including attributed child Context). Oversized records use the same authenticated byte endpoint, with `allowPartial=true&resourceKey={key}` on its byte GET for nonfinalized resources; full-Chat evidence stays gated on terminal native delivery. Every page uses the header cutoff; a partial page additionally requires the current committed Chat head to equal that cutoff. Missing terminal pages, changed cutoffs or foreign Chat/parent/Submission fail, never truncate. |
| Page API-owned billing | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/resources/by-key/{key}/billing?submissionId=...&after=...&limit=200&throughCount=...&throughSha256=...[&allowPartial=true&throughSeq=...]` | Paired **committed** `usageEvents` and model `billingSettlements`, source ordered, 200 pairs/4,000,000 bytes per page. Partial reads also bind the header's native cutoff. First page freezes `cursor:{throughCount,sha256}`; every later request and a final `limit=1` fingerprint probe supply both values and match the full API source (including when one page was enough). All pairs must reach `nextAfter:null` at the frozen count. Action/Tool facts come from the header, not a generation-to-billing join. An unknown/unsettled fee keeps billing coverage partial, not zero. |
| List evidence artifacts | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/evidence/artifacts?submissionId=...` | `{artifacts:[{path,size,mediaType}]}`: files the Agent produced in its own Space, excluding `/reference`, `/initial-materials`, `/userspace`, `/evidence` and uploads. |
| Read evidence file | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/evidence/files?path=...&submissionId=...` | Raw, streamed bytes of one listed file; `413` when it exceeds the package's `EVAL_EVIDENCE_FILE_MAX_BYTES` (`95_000_000` in `@springbrand/eval-harness@0.1.0-alpha.5`, which Eval pins; the limit is in effect). Eval omits larger artifacts as `too-large` before reading them. |
| Read evidence trajectory | `GET /internal/v1/eval-harness/users/{userId}/chats/{chatId}/evidence/trajectory?afterSeq=...&limit=...&submissionId=...[&throughSeq=...]` | `{format:"sp-pi-trajectory/v1",cursor:{throughSeq},records:[{ingestSeq,record} \| {ingestSeq,reference}],nextAfterSeq}`. A bounded page includes safe `pi-trajectory/v1` rows or immutable byte references; the first page freezes `throughSeq` (even when empty), and resumed/continuation reads pass it back. The terminal `submissionId` authorizes the whole SAFE Chat history, **not** a record filter: imported Context and earlier Submissions remain. Eval rejects a changed/regressed cutoff, foreign Chat/parent, unsafe/unprojected records and event-only pages. It caps each JSON page at 4,000,000 bytes; verified referenced bytes stream unchanged as one original v2 JSONL line directly into content-addressed storage, with a durable watermark and part cursor. Missing terminal pages, partial bytes and oversized single records never produce a success/manifest. `readFinalReply` checks only the last assistant of the exact selected Submission; a later omitted or oversized reply cannot be replaced by an earlier one. `409 EVIDENCE_NOT_READY` with `Retry-After` is retryable only for Harness GETs. The public package and serving SP deployment are still pending release/parity verification. |
| Import evidence file | `PUT /internal/v1/eval-harness/users/{userId}/chats/{chatId}/evidence/files?path=/relative` | Raw body with `Content-Type` and `X-Eval-Content-Sha256: <hex>` / `{path:"/evidence/...",size,sha256}`. Evaluator Chats only. Eval streams each stored blob (chunked, half-duplex) rather than buffering it, verifying size and SHA-256 against the manifest while it streams; a mismatch aborts the upload as a non-retryable error. An identical repeat is a no-op; different content is `409`, a path escaping `/evidence` is `422`, and a write after stop is `409`; none of these is retried. Eval writes the manifest last. The Run Worker gives Runtime `spEvidenceLimits(DEFAULT_EVIDENCE_LIMITS)`, so artifacts and trajectory parts are exported within `EVAL_EVIDENCE_FILE_MAX_BYTES`. Before any write Eval still checks every manifest file against it; a larger file (only possible in a bundle stored under larger limits) fails the import explicitly and permanently. |

The Run Worker process consumes pg-boss Run jobs, reads the persisted Run, its Project plan and ProjectSample snapshots, and composes Runtime with this Harness; on shutdown it stops fetching jobs and waits for active Runs. It uses this service contract; browser session tokens are never stored for background execution. This release's concrete Harness rejects `codex` and `cc` ("SP Harness cannot run {framework} Agents") rather than falling back to SP. Initialization does not send `runtime`; SP receives it when ensuring a Chat or submitting a prompt, while Eval uses it to bound terminal observation. Submission observation over WebSocket lives in `sp/submission-observer.ts`.

`start:worker` reads initial resources from `EVAL_BUNDLE_DIR`, the absolute directory shared with the API. For user `{ownerUserId}`, Bundle `{bundleId}`, Material `{materialId}` and Session `{sessionId}`, the files are `{root}/{ownerUserId}/{bundleId}/materials/{materialId}.json` in a Material Bundle and `{root}/{ownerUserId}/{bundleId}/sessions/{sessionId}.json` in a Session Bundle; every segment is a lowercase platform UUID, so no ID can act as a path segment, and the user directory isolates owners. A Material file is `{ "files": [{ "path": "/brief.txt", "mediaType": "text/plain", "contentBase64": "..." }] }` and must satisfy SP's Material file rules. A Session file is `{ "format": "json" | "jsonl", "content": "..." }` and is checked with SP's `readEvalCanonicalContext`, which owns the canonical entry format, duplicate-key handling and size limits. Resolved paths must stay inside the owner directory. Content under one ID is immutable; changed content conflicts with SP initialization facts.

A ProjectSample without materials needs no material file. Material and Session files referenced by a Project remain readable by ID after their catalog entries are soft-deleted. Any referenced material missing from its Bundle fails initialization explicitly. A referenced initial Context must resolve to its uploaded content; a missing file fails initialization rather than silently starting an empty Context.

## Readiness and large transfers

- **Not ready is not failed.** `409` with error code `EVIDENCE_NOT_READY` on a Harness `GET` (evidence artifacts, files, trajectory pages, output) means the Submission or its telemetry has not settled. Eval raises a retryable `SpHarnessError` with `status: 409` and SP's `Retry-After` as `retryAfterMs` (capped at 30 s by the HTTP client). Runtime's own bounded backoff schedules the repeat; the hint is carried for diagnostics. Exception: after a nonfinalized header and explicit post-wait opt-in, a partial page/byte GET still returning `EVIDENCE_NOT_READY` cannot be downloaded by repeating the same request (e.g. older SP without partial paging); that one download fails non-retryably and saves **no** fabricated snapshot. Any other `409` (for example `REQUEST_CONFLICT`) stays non-retryable, as does every `PUT 409`.
- **Size ceilings.** Each new resource header, native page and billing page is capped at 4,000,000 bytes before JSON decoding; none decodes the legacy combined resource body. Referenced native record bytes stream under the unchanged 95 MB evidence-file limit. A compact record/page that cannot fit its bounded temporary spool fails explicitly, not by omission. Other nonpaged JSON calls retain the existing V8 string-length ceiling; the new resource collector does not use it. No new record-count or fee budget silently drops facts.
- **Persistence ceiling.** A collected snapshot is stored outside stage facts in `eval_attempt_resources`, atomically with its summary and stage revision. Verified, body-free compact rows are sealed in a private temporary JSONL spool, replayed a bounded page at a time into a transaction-local PostgreSQL table, and projected into the existing JSON columns without materializing the whole result in JS. The spool is deleted on success/failure; historical raw rows and evidence bytes are unchanged. This SQL path has focused non-DB tests but still needs an isolated PostgreSQL integration test and cross-deployment verification before release.
- **Timeouts.** Control calls, including readiness, keep the 60 s request timeout and stop keeps 10 s. Each resource header/page/record byte read and evidence transfer uses a separate 5-minute transfer timeout (`transferTimeoutMs`), not a whole-operation timeout.
- **Cancellation.** Readiness and paged collection inputs accept `signal?: AbortSignal`, a local transport option that is not sent to SP or saved in a plan. The installed HTTP client's signal cancels the request and body read; referenced byte reads also physically cancel and discard their spool. Harness promises settle only after cleanup, so Runtime retains its process-wide download slot until the atomic save or abort. Cancelled reads are not retried or reported as resource failures.

## Waiting for resources

A snapshot is downloaded once after SP reports it final, or explicitly from known facts when the wait expires, instead of re-reading 100+ MB while waiting:

1. Runtime's shared resource flow checks the persisted download budget before any readiness or snapshot request. Transient reads use the existing ten-retry policy. Downloads are counted on the Attempt after acquiring the shared slot and before HTTP, so a crashed download counts too, while cancelling a queued task does not. Once the budget is spent the flow saves exhausted state, clears resource debt and reports it best-effort through `onError`; later recovery does not repeat the callback. A process holds one slot through count persistence, physical download and atomic snapshot save; readiness waits and download backoff are outside it.
2. When the Agent ends, Runtime polls the readiness route in the same pass after 5, 10, 20 and 40 s. As soon as `finalized` is true it downloads the full snapshot once.
3. If it is still not final, the stage keeps `resourcesPending` with a `deadline` ten minutes after the Agent ended; later Worker passes check readiness every 60 s until the deadline. A Run waiting for nothing else is woken by a delayed job at its earliest `nextAttemptAt`, so idle waits spend no retry. At the deadline Runtime sets the Harness's `allowPartial:true`, reads only complete frozen pages of already-known facts, and atomically stores their real counts with `finalized:false`, `coverage.partial` and SP's readiness. An interrupted page or changed header/billing fingerprint discards the spool; a later finalization during a partial read retries from a fresh finalized header rather than claiming finality from the old partial one.
4. A manual `resources` recollection starts the same wait with a new ten-minute deadline.

For an accepted Evaluator whose terminal receipt is still unconfirmed, budget admission precedes receipt inspection. Any confirmed terminal state and completion time are persisted before resource reads or clearing the wait; failed writes leave recovery scheduled. An already finalized snapshot is not downloaded again. Exhausted budgets skip receipt inspection entirely.

Eval does not trigger delivery of SP's telemetry/runtime outboxes; it only waits for it. Draining them on demand needs a guarded flush API in `@springbrand/agent-runtime` (follow-up).

## Diagnostics

The Harness accepts an optional `log(event)` sink (the Runtime's `RuntimeLog` type), wired by the Run Worker to the same pino sink as the Runtime log (`error` for `retry_exhausted`; `warn` for an event with `error`, `ws_reconnect` and `operation_retry`; otherwise `info`). Events carry identifiers (role, Chat, Sampling, Evaluation, operation key, Submission), HTTP status, declared byte counts and durations, never prompts, payloads, native records, file bytes or the service token; a failure's `error` is `errorDiagnostics` output, plus SP's `X-Request-ID` as `requestId` and Cloudflare's `cf-ray` as `cfRay` when the response carried them (`cfRay` only on evidence byte requests, whose raw headers the Harness reads). `resources_read` logs source coverage, usage/native-record/billing counts and readiness; `evidence_trajectory_page` logs failures and the final page's `from`, `pages` and `records` (not bodies). The existing WebSocket, file and import summaries remain payload-free.

## Initialization

One initialization call carries everything a Chat receives before its first Submission; SP keeps a single initialization fact per Chat, so the call is never split.

- `data.userPrompt` and the Submission's `prompt` use the package's shared `evalPromptSchema`: both must be nonblank strings, with leading/trailing spaces, line endings and Unicode whitespace preserved unchanged. Arbitrary Data business fields are retained. Eval consumes this contract directly, without trimming Prompt text.
- `initialMaterials` carries every material of the role in Data order: the Subject's `initialMaterials`, or the Evaluator's `evalInitialMaterials`, which Runtime passes as the Evaluator's own `data.initialMaterials`. Entry *i* has the same `{bundleId, materialId}` as entry *i* of `data.initialMaterials` and carries that Material's resolved `files`. The field is omitted when the role has no materials.
- SP writes each Material below its own root `/initial-materials/{bundleId}/{materialId}`,, so different Materials never share a path.
- `initialSession` is the single optional Session reference of the Subject; its resolved context is canonical JSON or JSONL. Messages use Pi's native format: assistant content is a block array with model, usage, timestamp and stop reason; user messages also carry a timestamp. A role/content-only transcript is invalid. SP's shared reader validates this format, and initialization rejects invalid history before reserving input facts or importing it. An Evaluator never sends one.
- `evaluationOutputSchema: {content}` is sent for every Evaluator and never for a Subject. `content` is the evaluation plan's JSON Schema text; SP writes it to the fixed path `/evaluation-output.schema.json`, independent of the Materials.
- Limits are SP's rules applied to the whole initialization: at most `EVAL_MATERIAL_MAX_FILES` (500) files per Material, `EVAL_INITIAL_FILE_MAX_BYTES` (5 MB) per file and `EVAL_INITIALIZATION_MAX_BYTES` (20 MB) in total across all Materials and the output Schema file. Eval rejects a Data field whose bound Materials exceed the total when it is written (see [Dataset upload](eval-dataset-upload.md)).
- The result `MaterializedDataBinding` is `{manifestHash, target, materials, evaluationOutputSchemaPath?}`: `materials` lists `{bundleId, materialId, rootPath}` in request order, and `evaluationOutputSchemaPath` is present only for an Evaluator.

## Eval control-plane resource APIs

Uploads and Data associations are separate authenticated Eval API operations; their routes and bodies are specified in [Dataset upload](eval-dataset-upload.md). The owner comes from the verified Eval SP session, never from a client field. Uploads write only to the authenticated user's Bundle directory, each under a newly generated resource ID; an existing resource file is never overwritten. Binding updates only the chosen Data references atomically and never uploads bytes; resource upload never edits Data. Pipeline and evaluation Run admission requires a Project evaluation plan; the Worker resolves the plan's output-schema ID to the saved, immutable Schema content.
