# Dataset upload and initial-resource catalog

The Dataset tab creates one prompt Dataset from a JSON or JSONL file. The file contains only Data rows; the create request carries Dataset `name` and `description` separately. Both fields are required, nonblank text. Every row requires nonblank `name`, `description`, `userPrompt` and `evalPrompt`. Prompt text is preserved. Other JSON business fields are allowed, but this upload route rejects platform IDs and initial-resource references; users select resources for each returned Data row after import. The existing general Dataset import remains available for execution-only data.

`POST /api/datasets/prompt-import` accepts JSON `{name,description,format,content}`. For `format:"json"`, `content` is a JSON array of Data objects. For `format:"jsonl"`, every nonblank line is one Data object. The API validates the whole input before one atomic Dataset/Data import and returns `{dataset,data}` with server-generated IDs. Both formats reject duplicate decoded JSON keys. File content is limited to 20 MiB; the request-body limit is derived from that content limit. Envelope, status and error codes follow [Eval HTTP control plane](eval-http-api.md); response shapes below are the success envelope's `msg` payload.

Material Bundle, Session Bundle, Material and Session catalog identities follow SP's UUID pattern, generated with `crypto.randomUUID()` by the Eval API. IDs are opaque and the UI displays required `name` and `description`. A Material Bundle contains only Materials; a Session Bundle contains only Sessions. They are two independent resource types with their own tables (`eval_material_bundles` with child `eval_bundle_materials`; `eval_session_bundles` with child `eval_bundle_sessions`), so one Bundle can never hold both. A Material is one file or a directory represented by its contained file paths. A Session is one canonical JSON or JSONL file; a Session Bundle has no folders. Resources enter a Bundle one at a time or through a [ZIP import](#zip-import). Bundle metadata and resource metadata are owner-scoped PostgreSQL records; file bytes remain in the owner-scoped `EVAL_BUNDLE_DIR`. No SP Durable Object storage is accessed.

| Operation | Route | Body / response |
| --- | --- | --- |

The Material upload preserves each file's workspace path and supports nested paths. Empty directories are not represented. Paths, the file count (1 to `EVAL_MATERIAL_MAX_FILES`, 500) and file shape follow SP's Material rules in `@springbrand/eval-harness`; each file is at most `EVAL_INITIAL_FILE_MAX_BYTES` (5 MB) and a Material at most `EVAL_INITIALIZATION_MAX_BYTES` (20 MB) in total. The upload route checks only that `files` is an array of objects with string `path`, `mediaType` and `contentBase64` (`422` otherwise); the catalog then applies the Material content rule once (`400 BUNDLE_FILE_INVALID` / `413 BUNDLE_FILE_TOO_LARGE`) and records the Material's decoded total as `byteSize`. Session content is parsed with the duplicate-key-rejecting `parseStrictJson` (the whole content for `json`, each nonblank line for `jsonl`) and then checked with SP's `readEvalCanonicalContext`, which consumes Runtime's single native history contract and owns the file format and size limits (`EVAL_SESSION_CONTENT_MAX_CHARS`, 2,000,000 characters, and `EVAL_SESSION_MAX_ENTRIES`, 10,000 entries). An output-format file is at most 1 MB. Resource references are bound at the individual Material or Session level, never to an entire Bundle. `initialMaterials` supplies Subject execution and `evalInitialMaterials` supplies evaluation; each is an ordered list of Material references whose shape rules are defined in [Package Boundaries](package-boundaries.md#eval-dataset). Every newly bound reference must name an active Material in an active Material Bundle of the owner. `initialSession` is one reference, supplies Subject execution only and newly binding it requires an active Session in an active Session Bundle of the owner. Existing references may be retained in the same Data field after soft deletion, including when editing other fields or replaying an identical Data import. A reference whose `bundleId` names a Bundle of the other type is not found. One Data may reference Materials from several Material Bundles and a Session from a Session Bundle. A Material or Session row commits only after its validated bytes are written, so binding checks only the catalog and never reads Bundle files. Every Data write path (binding PATCH, generic create, update and import) also sums the `byteSize` of the Materials one field lists, including retained references; a field over `EVAL_INITIALIZATION_MAX_BYTES` is `413 BUNDLE_FILE_TOO_LARGE` with `errors: [{path: "<field>"}]`, since SP initializes each role's Materials together. SP still enforces the exact total, including an Evaluator's output Schema file, at run time. Material Bundle, Session Bundle, Material, Session and output-format IDs in paths and references must be UUIDs; mixed case is accepted on input and stored and returned in lowercase. Re-uploading a Material or Session under the same generated ID is not part of this create flow.

Canonical Session entries use Pi-native messages. In particular, assistant `content` is a content-block array with `api`, `provider`, `model`, `usage`, `stopReason` and `timestamp`; a user message also has a `timestamp`. JSON contains `{entries:[...]}`, while JSONL contains one entry per nonblank line. Eval preserves the uploaded text and relies on SP's shared reader for native message validation, including malformed assistant content; it does not convert plain transcripts into native history. Demonstration inputs live in [Eval 联调数据](../fixtures/eval-demo/README.md).

## ZIP import

`POST /api/material-bundles` and `POST /api/session-bundles` with a `zip` file, and the `/import` routes, turn one ZIP archive into resources of the target Bundle. The whole archive is validated before anything is written: every entry is checked, every Material file follows the single-Material rules above and every Session follows the single-Session rules above. Any failure rejects the whole archive, and no Bundle or resource is created or listed. A successful import commits all its resources, and for creation the Bundle itself, in one database transaction; files written for a failed import are removed. Imports carry no idempotency key: retrying a request whose response was lost may create a second Bundle or duplicate resources, which the user deletes.

- Archive: its structure is checked by SP's shared strict-ZIP inspector (`inspectStrictZip` exposed by `@springbrand/eval-harness`), which rejects non-ZIP or corrupt archives; empty, absolute, `..`, backslash and otherwise unsafe paths; duplicate and case-insensitively colliding paths; symbolic links and other non-regular entries; encryption; compression other than stored or deflate; declared sizes that differ from the inflated bytes or checksums; and over-long paths. Every entry is treated alike: no wrapper folder is stripped and no entry such as `__MACOSX/` or `.DS_Store` is skipped. Eval then applies the Bundle type's layout rules below and validates each resource's content.
- Session Bundle: every entry must be a regular file at the archive root named `*.json` or `*.jsonl` (lowercase extension) with a stem before the extension, so a root file named exactly `.json` is rejected; any directory or nested path rejects the archive. Each file is one Session whose `format` is its extension and whose `content` is the whole file text, decoded as strict UTF-8.
- Material Bundle: each top-level directory is one Material containing every file below it, with paths relative to that directory (`case-a/assets/logo.png` becomes Material `case-a`, path `/assets/logo.png`). Each root-level file is one single-file Material (`brief.txt` becomes path `/brief.txt`). Directory entries carry no content, so empty directories inside a Material are not represented; a top-level directory without any file is rejected. A path used both as a file and as a directory is rejected. Any file type is allowed; `mediaType` follows the file extension and is `application/octet-stream` when unknown.
- Each resource's `name` is its top-level entry name (directory name, or full file name with extension), which must be nonblank after trimming like every catalog name; a blank top-level name rejects each entry below it. Its `description` is the target Bundle's description, and both are editable later. Each `imported` item's `source` is that same top-level entry name; items are ordered by entry path.
- An archive yielding no resource is rejected.
- Limits: the archive is at most 50 MB, its declared decompressed total at most 100 MB, with at most 5,000 entries, 500 resources and 768-character entry paths, where a Material archive counts its top-level entries and a Session archive counts every file; a Material file over its limit is rejected before it is inflated; per-resource limits above still apply. All are defined in `apps/eval-api/src/limits.ts` and listed in [Eval HTTP control plane](eval-http-api.md#request-bodies-and-limits).

Invalid archives, entries and content are `400 BUNDLE_FILE_INVALID` and exceeded archive or Material limits are `413 BUNDLE_FILE_TOO_LARGE`; Session size limits belong to SP's canonical-context rule and are reported as `400 BUNDLE_FILE_INVALID`. Their `errors` items are `{path, errMsg}`, where `path` is the ZIP entry path, suffixed with `:<line>` for a JSONL line, or the Material's top-level name for a failure of the whole Material (file count, total size). Strict-ZIP inspector violations stop at the first one and report only it, under its entry path or `path:"zip"` for the archive itself (not a ZIP, corrupt, too many entries, decompressed total over its limit). Layout and content errors are collected for every entry; the first exceeded limit ends collection and is reported alone as `413`. At most 100 items are returned.

## Catalog rules

Every route runs as the fixed Eval SP service account. The API takes the owner from that account, never from the body. Catalog queries and writes use the owner in SQL, and Bundle file writes use the same owner directory. Missing Bundles or resources return `404`.

An output format is one standalone, immutable draft 2020-12 JSON Schema file. It has a server-generated UUID, required `name` and `description`, and no Bundle. The catalog validates and stores the parsed Schema. A Project's evaluation plan selects one output format by ID and fixes its content digest; the plan can be replaced only until the first pipeline/evaluation Run locks it (see [Eval HTTP control plane](eval-http-api.md)). Runtime reads the Schema by that ID before initializing each Evaluator, and Metrics validates evaluation outputs against it. A missing, deleted or another owner's output format cannot be selected.

Uploaded Material files, Session content and output Schema content have no edit operation. Names and descriptions can be changed without uploading again. Dataset and Data already expose full metadata updates; the per-Data resource binding PATCH replaces or clears each present field's whole value.

All catalog deletes use the SP-style `deleted_at` marker and hide deleted entries from list/detail queries. Material, Session, Bundle and output-format deletion is allowed even while Data or Projects reference them; deleting a Bundle also marks its active resources deleted. Deleted resources retain their database records and uploaded bytes. Existing Data bindings are never cleared automatically and continue working when the Data is edited or used to create a Project; existing Projects keep reading by ID. New Data or a new binding cannot select deleted resources. A retained Material may be reordered or removed within its original field, but moving it between `initialMaterials` and `evalInitialMaterials`, or restoring it after removal, is a new binding. Dataset and Data deletion also use `deleted_at`; Projects copy Dataset and Data into their own snapshot, so deletion never affects them. A Data still associated with an active Dataset cannot be deleted.

Prompt Datasets keep an internal kind marker. Their nonblank Dataset description and each member Data row's nonblank name, description, `userPrompt` and `evalPrompt` remain required after import. Generic Data and Dataset APIs still support execution-only rows, but updates and membership changes cannot weaken an existing Prompt Dataset. Every Data creation, update and general import validates new Material and Session references against active resources owned by the authenticated user; references cannot bypass the catalog by using the generic routes.
