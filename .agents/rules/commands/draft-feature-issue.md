# draft-feature-issue

把当前需求整理成一份简洁、可以交给开发的功能大纲。这个命令只生成内容草稿，
不会在任何任务系统中创建或修改 Issue。

保持内容简短。这是一份 Issue 大纲，不是 PRD、设计文档或实施计划。

## 处理流程

1. 根据当前对话和引用的资料理解需求结果。
2. 只写已经确定的产品决策，不猜测缺失的行为、API 契约或技术限制。
3. 只有在缺失决定会明显改变功能或验收结果时，才提出一个聚焦的澄清问题。
4. 使用下面的模板输出需求大纲。

## 编写规则

- 用一到两句话写清目标。
- 列出三到八个具体功能点。
- 不单独创建“交互细节”章节。骨架屏、确认步骤等特殊交互，写进对应功能点或
  验收标准。
- 只有当需求新增或修改 API、数据、权限、校验或资源处理时，才保留
  `API / 数据要求`。
- 引用共享技术规范，不把整份规范复制进 Issue。
- 验收标准必须是可以观察和判断通过或失败的结果，避免“正常工作”“妥善处理”
  “优化体验”等模糊表达。
- 没有内容的可选章节直接删除。

## 输出模板

```markdown
# <功能名称>

## 目标

<谁需要这个功能、解决什么问题，以及预期结果。>

## 功能点

- [ ] <功能点一>
- [ ] <功能点二>
- [ ] <功能点三>

## API / 数据要求

- <需要新增或修改的 API>
- <重要的请求和返回数据>
- <权限、校验、存储或资源要求>

## 验收标准

- [ ] <可以观察的用户结果>
- [ ] <可以验证的 API 或数据结果，如适用>
- [ ] <重要的失败、权限或持久化行为>
- [ ] <要求的测试或验证通过>

## 补充

- 设计稿：<链接或引用>
- 技术要求：<只写本需求特有的限制>
- 不包含：<明确不做的内容>
```
